# Infraestrutura de testes end-to-end

Status: approved by Luis on 2026-10-28
Branch: feature/testes-e2e

## Por quê

Os fluxos do Sagyou atravessam renderer, IPC, processo main, SQLite e APIs nativas do Electron. Os testes unitários não demonstram que esses caminhos funcionam juntos nem que um backup restaura dados no app. O isolamento é obrigatório: testes não podem abrir ou modificar o `userData` real.

## Objetivos

- Executar testes E2E reproduzíveis no GitHub Actions, com uma instância Electron e um diretório temporário exclusivo por teste.
- Cobrir, na primeira leva, board, financeiro, arquivos, backup e senha.
- Permitir testar o caminho agente → MCP → aprovação → store → tela com um CLI falso, em uma etapa posterior da mesma infraestrutura.
- Produzir capturas de tela de dados sintéticos para revisão de mudanças visuais.

## Fora do escopo

- Executar E2E no computador do desenvolvedor.
- Reutilizar o banco, a senha, arquivos ou configurações pessoais de uma instalação Sagyou.
- Simular serviços de IA reais ou depender de rede externa durante os testes.
- Modificar o formato dos dados de produção para acomodar testes.

## Decisões de Luis

- E2E roda somente no GitHub Actions, com Electron em `xvfb-run -a`.
- A primeira leva cobre board, financeiro, arquivos, backup e senha.
- A task 6 adiciona rótulos acessíveis e seletores estáveis sem alterar o visual.
- A integração MCP será coberta por um CLI falso na task 13.

## Decisões do construtor (o agente decidiu; o humano pode mudar)

- **Diretório de dados:** usar `SAGYOU_E2E=1` junto com `SAGYOU_USER_DATA_DIR=<diretório temporário>`. O bootstrap do main resolve e valida esse caminho antes de carregar módulos que consultem `app.getPath('userData')`, pois `src/main/store.ts` calcula `DB_PATH` na importação. Não depender de `--user-data-dir` até comprovar seu comportamento com Electron 39 no CI. Um teste específico documentará o resultado dessa verificação; se a flag funcionar, a variável explícita ainda será usada pela trava de segurança.
- **Trava:** em modo E2E, recusar a inicialização se o caminho estiver ausente, não for absoluto, apontar para a raiz temporária em si, escapar de `os.tmpdir()` após resolver links simbólicos, ou coincidir com o `userData` normal. Falha fechada antes de abrir banco, logs, backup ou janela. Fora de E2E, ignorar a variável de override.
- **Estado inicial:** presets JSON sintéticos no formato de `SaveData`, aplicados pelo `saveData` oficial no main isolado antes de mostrar a janela. Assim, o schema e as migrações continuam de propriedade de `store.ts`; o harness não escreve SQL próprio. Presets: `empty`, `board`, `finance`, `locked`. Para senha, usar o fluxo de configuração oficial no ambiente de teste. Cada teste ganha IDs próprios e diretório exclusivo.
- **Capturas:** 1280×800 e 1920×1080, nos temas claro e escuro. Capturas saem só de presets sintéticos e são anexadas como artifact do CI.
- **CLI falso:** entra na task 13, depois do isolamento, dos presets e dos helpers de APIs nativas. Aceita roteiros locais fixos, somente em `SAGYOU_E2E=1`; o renderer nunca escolhe executável.
- **Dependência:** adicionar `@playwright/test` com versão exata registrada no lockfile quando o plano aprovado for construído. Avaliar a remoção de `playwright-core` após verificar os consumidores. Um worker por vez, trace preservado em falha, `forbidOnly` no CI.

## Comportamento

- O helper `launchSagyou` cria uma pasta com `mkdtemp` dentro de `os.tmpdir()`, prepara o preset e inicia o Electron apontando para ela. `close` encerra o processo antes de apagar somente essa pasta.
- Em modo E2E, o app não abre DevTools, não procura atualizações, não registra atalhos globais e não executa migração legada de chat. A saída de rede do app é bloqueada; os testes controlam respostas locais necessárias.
- O teste de fumaça confirma a janela inicial e a existência de `kanban.db` no diretório temporário. Testes de persistência fecham e reabrem o app no mesmo diretório do próprio teste.
- Diálogos nativos de abrir/salvar e `shell.openPath`/`openExternal` são substituídos por helpers do harness após abrir a janela, antes de disparar a ação.
- Seletores usam papel e nome acessível primeiro. `data-testid` fica restrito a elementos sem texto estável: card, coluna, transação e toast.
- Fluxos com dados persistidos verificam também o estado após reiniciar. Backup inválido deve preservar os dados existentes; o índice de busca deve ser reconstruído na importação válida.
- O job E2E publica traces de falha. As capturas são artifact separado, gerado sob demanda ou por condição explícita no CI.

## Dados

Nenhuma alteração no schema ou no formato de backup de produção. Testes criam `kanban.db`, arquivos, senha e configurações apenas sob um diretório temporário exclusivo. A proteção usa a raiz temporária resolvida, nunca um caminho fornecido pelo renderer. A limpeza ocorre só após o processo encerrar e só sobre a pasta criada pelo próprio teste. Um erro de configuração encerra o processo antes de qualquer acesso aos dados reais.

## Telas

Nenhuma tela nova. A task 6 apenas acrescenta nomes acessíveis aos botões de ícone e atributos de teste onde o texto não identifica o elemento. Capturas representam Home, Board, Financeiro, Arquivos, Metas, Hábitos, Memória, Configurações e Fleet vazio, nos tamanhos e temas definidos acima.

## Sequência e critérios de aceite

1. Isolamento de `userData` e trava contra dados reais, com teste unitário e verificação no CI.
2. Playwright para Electron, helper de lançamento e teste de fumaça verde no CI.
3. Presets sintéticos e helpers para diálogos/APIs nativas.
4. Seletores acessíveis e testes dos fluxos de board, financeiro, arquivos, backup e senha.
5. Capturas como artifact, job E2E completo e CLI falso de MCP com casos de aprovação, expiração e cronômetro.

Cada etapa segue seu plano aprovado, recebe revisão, typecheck, testes, lint sem erros novos e PR sem merge pelo agente. Os testes E2E rodam somente no CI.
