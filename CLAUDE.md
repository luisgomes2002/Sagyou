## Workflow

Source of truth: [`docs/workflow.md`](docs/workflow.md); `AGENTS.md` carries a summary every tool reads (keep it in step), and `GEMINI.md` / `.github/copilot-instructions.md` are pointers to it. Stages: spec → plan → build → review → PR, with human gates at spec approval, plan approval and merge. Agents never approve their own spec/plan and never merge. Never commit to `main` or force-push; use `feature/`, `fix/`, `chore/<slug>` and Conventional Commits; commit/push only when the developer asked to ship. Bugs: no fix without root cause, failing test first, stop after three failed fixes.

Project skills (`.claude/skills/sagyou-*`) cover each stage — **start the matching one on your own**: new feature → `sagyou-spec` (approved spec → `sagyou-plan` → `sagyou-build` → `sagyou-review` → `sagyou-pr`); something broken → `sagyou-fix`. In this repo they take precedence over generic plugin workflow skills. Subagents in `.claude/agents/` (`sagyou-plan-checker`, `sagyou-implementer`, `sagyou-reviewer`, `sagyou-test-runner`) each have a single role; reviewers are read-only. Shared permissions are in `.claude/settings.json` (deny: force-push, `--no-verify`, reading `.env*`).

## Architecture

The app is a frameless Electron window split into three processes. **AI in the product means running a code-agent CLI (Codex, Claude Code, OpenCode) in a terminal.** There is no generic API chat, no conversation history, no API keys and no token-spend tracking; see "Remoção do chat genérico" below for what was removed and how existing data was migrated.

**Main** (`src/main/`)

`index.ts` and `handlers/` are the process entry and IPC orchestration; `store.ts`
owns SQLite persistence. Domain implementation lives in `modules/`: `agent/`
(executor session, PTY, worktree, diff, delivery, MCP, run archive and terminal handoff),
`ai/` (memory, skills, the legacy-chat removal migration and the eval core),
`conversations/` (only `legacy-ai-data.ts`, the read-time `ai-config.json` normaliser),
`files/` (attachments, backup, image bytes and document parsing), `code/` (source access and
diff), `search/` (derived FTS5 index and queries), `security/` (app lock),
`web/` (safe fetch, render and external links), and `financial/` (exchange rates). Imports should use the
domain module path; do not add domain implementation back to the main root.

The main window sends only credential-free `http:`/`https:` URLs through `safeExternalUrl` to `shell.openExternal` and blocks navigation away from its app page. Do not hand renderer-provided URLs directly to OS protocol handlers.

- `index.ts` — creates the BrowserWindow and registers IPC for `window:*`, `store:*`, `backup:*`, `files:*`, `excel:*`, `search:*`, `security:*`, `legacy-chat:*` and the remaining `ai:*` channels (config, memory, skills, harness status, code-agent/terminal sessions, run archive). It owns the executor launch (`ai:code-agent:run`) and the `ai-config.json` read/write. At startup it runs the one-time legacy-chat removal **before** `createWindow()` (see "Remoção do chat genérico").
- `ai-config.json` now holds only agent configuration (`codeHarness`, `userName`, `reasoningEffort` and any key a newer build wrote). `normalizeLegacyAIConfig` (`modules/conversations/legacy-ai-data.ts`) reads `codeHarness: 'sagyou'` as `codex`; `saveAIConfig` **merges** over the file and drops the 14 retired chat keys on both sides (`stripLegacyApiConfig`), so an unknown key survives and no API key can come back through `ai:config:set`. `ai:config:get` never returns keys.
- `handlers/window.ts` — owns `createManagedWindow` (window creation, navigation policy, external-link routing and renderer-flush close protocol) and `registerWindowHandlers(ipcMain, getWindow)`. ⚠️ The IPC registration takes a **getter** `() => mainWindow`, not the value — it's called before window creation, so capturing `mainWindow` directly would be `null`.
- `handlers/files.ts` — `registerFilesHandlers(ipcMain, deps)`. File upload/download/delete, Excel export and task images (`task:images:*`). Deps include `dialog`, `shell` and the image directories.
- `handlers/backup.ts` — `registerBackupHandlers(ipcMain, deps)`. Backup export/import + `ai:import`. Manages the blob collectors/restorers for file and task-image bytes during backup.
- `handlers/memory.ts` — `registerMemoryHandlers(ipcMain, deps)`. Owns the memory IPC channels and their shared lazy decay pass; receives store and memory rules through injection, while memory still lives outside `persistAll`.
- `handlers/code-files.ts` — `registerCodeFilesHandlers(ipcMain, deps)`. Owns the read-only `ai:code:list/read/search` IPC channels; path confinement and asynchronous walking remain in `main/modules/code/code-files.ts`. They are exposed by the preload but **no renderer code calls them today** (their consumer was the chat); the spec keeps them as cleanup candidates.
- `handlers/legacy-chat.ts` — `startLegacyChatRemoval` (runs the migration, records the first snapshot dir, never throws) and `registerLegacyChatHandlers` (`legacy-chat:notice` / `legacy-chat:dismiss`).
- `global-search-index.ts` — builds typed search documents from saved records and memories. **Conversations are no longer indexed.** `global_search_fts` is a disposable FTS5 table: `store.ts` rebuilds it from SQLite on startup or through `rebuildSearchIndex()`. App saves synchronize it inside the source transaction; memory writes do the same. Backup import calls `store:rebuild-search-index` after the store and memories finish restoring, so old hits are removed; the legacy-chat removal rebuilds it too. Search metadata includes project/profile/table scope and separate project/memory archive flags. Never treat this index as a source of truth or put it in backups.
- `global-search-query.ts` — read-only `search:global` and `search:global:get` IPC, typed in both preload files. Text search builds a quoted FTS5 prefix query from Unicode words, ranks title > tags > content with `bm25`, and returns bounded snippets plus the full match count. Both text and type/ID lookup restrict every financial type to the active profile; financial rows without a profile ID are hidden. Archived projects and memories are separate opt-in filters. The global search does not bump memory access counters.
- `SearchModal.tsx` — Ctrl+K uses `window.electronAPI.search.global`, groups hits by area, filters by type and project, and pages with the response's total/hasMore. It keeps keyboard selection on the input with arrow keys and Enter; Escape closes the dialog. The renderer also hides financial hits whose profile ID no longer matches the active profile while an IPC response is in flight. `App.tsx` passes the selected hit to its destination: cards and rows scroll into view and highlight, planner records open their editor, and transaction details open their parent transaction. Financial hits route to their table and relevant tab; dated hits select their month.
- Project documents contribute parser text to their existing `file` FTS row. `file_search_content` is a disposable SQLite cache keyed by `file_id`, with no FK because `persistAll` temporarily deletes every `files` row. Upload parses supported files after copying; startup/rebuild refreshes existing files; deletion removes both cached text and the FTS row immediately. MarkItDown is a platform-native PyInstaller resource made by `npm run prepare:markitdown` on each release runner and copied by electron-builder; the user never installs Python, and the main process must never fall back to a `python` found on PATH.
- `modules/files/image-files.ts` — image bytes as **files** (`decodeDataUrl`, `readImageAsDataUrl`, `deleteImageFiles`, `mimeForExt`), now used only by task images (`userData/task-images/`) and `store.ts`. `decodeDataUrl()` refuses non-image data URLs rather than writing whatever it's handed under an image's name. The chat-only half (`isImageFileName`, `saveImageToDir`) went away with the chat.
- `skills.ts` — Skills: `.md` files in `userData/skills/`. IPC: `ai:skills:list/save/delete/import`. In a session launched **with an initial request**, up to 20 skills (bounded, secret-scrubbed) go into the executor brief; no renderer UI calls the skills IPC today.
- `web-fetch.ts` — backs `ai:web:fetch`: native `fetch`, 15s `AbortController`, response capped at `MAX_CONTENT_CHARS` (8000), returning `{ content, url, truncated }` or `{ error }` (`url` is the **final** one, after redirects). The channel is still registered and exposed by the preload, but nothing in the renderer calls it since the chat went away; the security rules below stay load-bearing for whoever reuses it.
  - ⚠️ **The URL comes from a model or a page, so it is untrusted.** This app runs on the user's own machine, where "the network" means their dev servers, NAS and router. So: **http(s) only** (`file:` would read the disk), **private/loopback/link-local/metadata hosts blocked** (incl. `::ffff:127.0.0.1` and `169.254.169.254`), and **redirects are followed by hand** with the same policy re-applied to every hop — `redirect: 'follow'` would let a public URL 302 straight into all of it. Entry URL and every hop go through one `validate`; no path is exempt.
  - **Embedded credentials are refused** (`http://user:senha@host/`), on entry and on every hop. Read off `url.username`/`url.password`, **never off the string** — `@` is legal in a path or query (`http://example.com/?x=a@b` has no userinfo), so a string test for '@' refuses ordinary URLs; and `http://:senha@host/` is userinfo with an empty username, hence both fields. This is depth, not a live bypass: `isPrivateHost(url.hostname)` already resolves `http://evil.com@127.0.0.1/` to 127.0.0.1 correctly. The reasons it goes anyway: forwarding credentials picked up off a page is a decision nobody made, and `http://google.com@evil.com/` reads as google.com in the `FetchOk.url` shown back to the user.
  - **The parser is the sanitiser, and the only one.** `new URL()` implements WHATWG, which strips ASCII tab/newline/CR _before_ parsing — so `http://exa\nmple.com` is example.com, a CRLF meant for header injection lands percent-encoded and inert inside the path, and `.trim()` covers the rest. ⚠️ **Never add a hand-rolled cleaning pass in front of it** — no character stripping, no HTML-entity decoding. The invariant holding this together is that **the URL checked is the object fetched**: `fetchWeb` validates a `URL` and hands that same `URL` to `fetch`, so nothing re-parses a string and reaches a different host. A text pre-pass breaks exactly that. HTML entities are a different encoding layer besides (URLs are percent-encoded); decoding `?a=1&amp;b=2` to `?a=1&b=2` silently fetches another query. All of this is pinned by tests, including one that fails if someone implements "reject URLs containing @" literally.
  - **Fetches are paced by waiting, not refusing** (`createRateLimiter`, `RATE_LIMIT_MAX` 10 per `RATE_WINDOW_MS` 60s, sliding): an accidental loop must not hammer a site from the user's own IP, and a caller that cannot sleep gets a delay rather than an error. `MAX_QUEUE_WAIT_MS` (2 windows) refuses only a hopeless queue. ⚠️ **The slot is acquired before the `AbortController` timer starts** — `timeoutMs` is the page's budget to respond, not the queue's. One slot per **logical fetch**, not per hop, and junk URLs are rejected on shape **without** spending a slot. The limiter is **process-wide module state**, so tests must inject their own (`FetchDeps.limiter`).
  - **The request carries nothing of the user's**, pinned by tests rather than asserted by a comment: exactly `host`, `connection`, `accept`, `accept-language: *`, `accept-encoding`, `sec-fetch-mode`, `user-agent: node` — no cookie, no `authorization`, no `referer`, across redirects too. The guarantee is a property of the **runtime, not of this file** (a Node release with a cookie jar, or a refactor onto Electron's `net.fetch`, would each pass review in silence), hence the tests. ⚠️ `mode` and `credentials` are both inert in Node: `credentials: 'omit'` is declarative, not load-bearing. Don't add `mode: 'no-cors'`, don't brand the user-agent, and don't drop it (many servers 403 a request without one).
  - The cap is applied **while reading**, not after: `res.text()` would pull a multi-gigabyte response into memory. Non-textual content-types are refused. Not covered: **DNS rebinding** (a public name that resolves to 127.0.0.1) — literal IPs and `.local`/`.internal` are.
- `web-render.ts` — the **JS-capable sibling** of `web-fetch`, reached via `ai:web:fetch` with `render: true`: SPA pages come back as text via a **headless render** in Electron's already-bundled Chromium (a hidden `BrowserWindow`; `session.webRequest` gives request interception natively).
  - ⚠️ **A browser is a far larger SSRF surface than `fetch`, and closing it is the whole point of this file.** It runs the page's JS and loads every subresource, and **none of those go through `fetchWeb`'s by-hand redirect check**. So **every request — main document and every subresource — is run through the same `checkUrl` policy** (`shouldCancelRequest`) via `session.webRequest.onBeforeRequest` and cancelled if refused; the main frame is additionally guarded on `will-navigate`/`will-redirect`. The context is an **ephemeral in-memory session** (no cookie jar), `sandbox` on, no node integration, no preload, images off, popups denied, WebRTC's non-proxied UDP disabled. The user-agent is scrubbed to plain Chrome (`plainChromeUA`).
  - Paced by the **same `defaultLimiter`** as `fetchWeb`. The pure pieces (`shouldCancelRequest`, `plainChromeUA`) are pinned in `web-render.test.ts`; the `BrowserWindow` orchestration **can't run under vitest** and must be **verified in-app**. ⚠️ Residual risks, documented not hidden: **DNS rebinding**, and a **subresource redirect** to a private host (relies on `onBeforeRequest` re-firing for the new URL).
- `code-files.ts` — `confineToRoot()` + `walkFiles()`, backing the `ai:code:*` handlers. **Async on purpose, and it must stay that way**: these run on the main process's event loop, which also serves IPC and the window controls (the sync version starved the loop for the walk's full duration). `confineToRoot` is the only barrier between a caller and the rest of the disk (note `base + sep`, or `/project-evil` passes as a child of `/project`); it's tested in `src/main/__tests__/code-files.test.ts`. Scoped reading (`detectSymbols`/`extractSymbol`/`extractLines`, pure and tested) is regex/brace-matching best-effort, not an AST, on purpose.
- `store.ts` — persists state to a **SQLite database** (`better-sqlite3`) at `app.getPath('userData')/kanban.db` (`kanban-dev.db` in dev). Opened in WAL mode with foreign keys on. Each save is a full replace inside a transaction (`persistAll` deletes children→parents, then re-inserts; later saves in the same session go through `persistDiff`). One-time `migrateFromJson()` runs on first boot: if the legacy `kanban-data.json` exists and the DB is empty, it imports it and renames the file to `.migrated`. The `kanban-data.json` format now only survives as the backup/export shape (produced in the renderer), **not** as the storage format. `readSetting`/`writeSetting` read and write single `settings` rows outside the full-replace save; `copyDatabaseTo` makes a WAL-safe copy of the live DB (`db.backup`).
- `security.ts` — derives the optional app-password key with `scrypt` and a random salt. Its config lives in `password-security.json`, mode 0600, **outside SQLite and every backup**: a data restore must never replace the local credential. `App.tsx` waits for `security:status` and only calls `loadData` after a successful unlock; do not move that bootstrap later or protected data flashes before authentication. `security:status` exposes only the optional display name used by the lock-screen greeting before authentication, never the AI config or any protected app data. A present but malformed/unreadable password file is `corrupt`, never treated as no password: the app stays locked until the user explicitly confirms `security:recover`, which removes only the broken credential file.

**Preload** (`src/preload/index.ts`)

- Bridges IPC to the renderer via `contextBridge`, exposing `window.electronAPI`. Its public type is derived from the actual `api` object in `index.ts`; `index.d.ts` only installs that type on `Window`. Never recreate a manual method list there, or preload and renderer can drift apart again.

**Renderer** (`src/renderer/src/`)

- Single-page React app. Entry point is `main.tsx` → `App.tsx`
- All state lives in one Zustand store: `store/kanban.ts` composes the slices in `store/slices/`
- `App.tsx` owns all modal state and UI event handlers, passing them as props down to views and modals
- There is no renderer tool layer, no `store/aiRun.ts` and no chat component any more. `src/renderer/src/ai/` holds only `system-prompt.md`, kept because `npm run eval` (`eval/live.ts`) and `eval-live.test.ts` still read it; it has no runtime consumer in the app.

### State layer

`store/kanban.ts` exports `useKanbanStore` (Zustand). It composes 9 domain slices from `store/slices/` (projects, tasks, financial, habits, goals, notes, planner, files, backup) plus the core lifecycle (`loadData`, `_persist`, `_flushPersist`). Every mutation calls `_persist()` internally, which serializes the full state and calls `storage.save()` — the payload is sent over IPC and written to SQLite by the main process (see Main above).

`store/normalization.ts` owns the load/import migrations shared by `kanban.ts` and `slices/backup.ts`, including decimal-string money and legacy code-path selection. Any future load/import path must use the same normalizers.

Storage is injected via `IStorageAdapter` (`services/StorageAdapter.ts`): `load/save`, `exportBackup/importBackup`, `importAIJson`, `loadMemories/replaceMemories` and the file helpers. In production, `ElectronStorage` is used (calls `window.electronAPI`). `WebStorage` is a parallel `localStorage`-backed implementation kept for an eventual browser build — it is not wired up in the app, but it must keep satisfying `IStorageAdapter`, so a change to that interface means changing both adapters. In tests, `ElectronStorage` is vi-mocked in `__tests__/setup.ts`. The adapter has no conversation methods any more.

`uiPreferences` holds the global theme, text scale and accessibility switches. It is normalized to safe defaults on load; when an older backup lacks the optional key, import retains the local choice instead of resetting the user's accessibility setup.

`loadData` and `importBackup` normalize every incoming `FinancialTable` through `normalizeFinancialTable` in `store/normalization.ts` — this fills missing arrays, defaults the currency, and **migrates monetary fields from legacy `number` to canonical decimal string** (see Data / Schema safety). Do the same for any new load path.

Soft deletes use a `Tombstone[]` array. On `importBackup`, all local state is replaced wholesale by the backup file — no merge. The helper functions `mergeEntities`, `mergeSprints`, `mergeHabits`, and `mergeTombstones` remain in `store/kanban.ts` but are unused.

### Views

`App.tsx` renders one view at a time based on `activeView` state (`home`, `board`, `canvas`, `done`, `goals`, `habits`, `financial`, `upcoming`, `reports`, `files`, `ai`, `memory`, `planejamento`, `graph`, `guide`, `settings`). **The `'ai'` key now means the Fleet**: it was kept (renaming it would be churn in `App`, `Sidebar` and the feature flags), and the sidebar item is labelled "Sessões de código". There is no `agents` view and no Chat item.

`board`, `canvas`, and `files` share the project-scoped layout, so they are selected by a nested branch in `App.tsx` rather than the top-level one.

**Fleet (`FleetView.tsx` + `components/ai/fleet/`)** is a three-part workspace: the session rail (`SessionRail`), the selected session in the centre (`AgentTerminal` or `CodeDiff`, via `Workspaces`) and an inspector. `NewSessionPanel` asks for the scope (a project with an authorised code root, or a general session) and the harness, and opens the session **blank, straight on the CLI's own screen** (`blank: true`): no form for a request, no pasted briefing. The user types the request to the CLI like running `claude` or `codex` in a terminal; each CLI keeps its own history. State is derived from main (`useCodeAgentRuns`, `ai:code-agent:*`), the view keeps no copy, and `retainThread` only remembers the selection when `FleetView` is unmounted by navigation (the PTY belongs to main). ⚠️ **Each live PTY keeps one xterm in the renderer (`components/ai/liveTerminals.ts`) until its `ai:code-agent:exit`**: a session switch or navigation detaches its element and re-attaches it, and a hidden terminal keeps receiving chunks from one shared `ai:code-agent:output` listener. Never go back to rebuilding the xterm from `terminal-reconnect` on every switch: main keeps only the last 8000 raw characters (`MAX_AGENT_LOG`), which start mid-redraw for a full-screen CLI, so the screen came back blank or scrambled; reconnect is only for the first mount after a renderer reload. Likewise `useCodeAgentRuns` appends `ai:code-agent:output` chunks to `run.log` locally, coalesced every 50ms; calling `status()` per chunk sent every run's log over IPC for every chunk of every terminal and made each extra session slow the others down. The sidebar item carries a live badge with the running-session count. The first time the Fleet opens after the legacy-chat removal it asks main for `legacy-chat:notice` and shows a dismissible notice with the snapshot folder; dismissing calls `legacy-chat:dismiss`.

### Agentes de código e IA

Everything AI-related is a code-agent session; the app no longer calls a model by API.

- `ai:harnesses:status` discovers Codex, Claude Code and OpenCode (installed, version, authentication, verified capabilities). `AIConfig.codeHarness` selects one; an unknown value falls back to `codex`.
- **Diagnostic log (`modules/logs/logger.ts`).** Main-process events go to `userData/logs/AAAA-MM-DD.jsonl` (local day, 14-day retention, outside every backup; past 5 MB a day only `warn`/`error` are written) via the app-wide `log` (a no-op until `configureLog` runs in `whenReady`, so tests and early startup are unaffected). Each line is `{ ts, level, area, event, msg?, data? }`; `data` keeps primitives only, strings pass `scrubSecrets` and are cut at 500 chars, and the keys `token`, `content`, `body`, `title`, `description`, `amount`, `value`, `args`, `arguments`, `password` are always dropped. ⚠️ Never log task/note text, money values, MCP tokens or tool arguments — log IDs, counts and outcomes. Logging failures are swallowed. Areas: `app`, `store` (migrations), `backup`, `pty`, `mcp` (`tool_call` with outcome/ms, `approval`), `delivery`. Use `log.*` instead of `console.*` in main.
- **The MCP bridge (`modules/agent/sagyou-mcp.ts`)** is how a CLI reaches Sagyou data. Read tools: `list_projects`, `read_tasks`/`read_project`/`read_notes`/`read_goals`/`read_financial_data` (paged), `search_memory`, `read_memory`, `list_recent_memories` (newest-updated first with no term; filters `type`/`status`/`since`/`until`, paged, max 50, snippets only, never touches decay), `check_memories`, `ler_tasks`, `ler_financeiro`, `ler_projeto`, `read_logs` (diagnostic log, filters `level`/`area`/`since`, max 200); legacy writes `save_memory` and `criar_task`; plus the 37 write tools below. `search_conversations` and `read_conversation` were removed with the history. Writes (`save_memory`, `criar_task`) go through the per-run approval queue (`mcp-write-queue.ts`); permissions are checked on every call.
- **MCP write tools (`modules/agent/mcp-write-tools.ts`)** add 37 writes: projects and columns, tasks (edit, move — across projects too — complete, reopen, delete, and the timer: `start_task_timer`, `stop_task_timer`, `add_time_spent` 1–86400 s), goals, notes, finance and memory. `MCP_APPROVAL_REQUIRED` decides the card **by tool name only**: every delete, archiving a project, every money write, creating a financial table and creating/renaming a financial profile; the rest run without a card. The run's auto toggle never answers a risky card (`autoApprovesPending`), and writes are refused until the renderer store is loaded (`isLoaded`), so a lock screen or reload can never flush an empty store over the database. A test pins that set and that every tool is classified exactly once — keep it that way when adding one. Every write, card or not, runs through the same per-run queue, which checks the run is still live before preparing and again before executing. Data writes are validated in the **renderer** against the live store (`services/mcpActions.ts`), in two phases over `store:mcp:action`: `prepare` validates and returns the card's `resumo` without writing; `apply` re-runs the same checks, calls the existing slice action and flushes. Main never imports the renderer, so the channel types are mirrored in `mcp-write-types.ts` / `types/mcp-actions.ts` (a test compares the tool lists). Memory writes stay in main (`prepareMemoryWrite`, then `upsertMemory`/`archiveMemories`/`deleteMemory`). Rules worth keeping: finance is confined to the session's captured profile (another profile's table answers exactly like a missing one); a debt-payment transaction is never edited or deleted over MCP; `delete_column` refuses a column with tasks (the slice action would delete them); the MCP never renames the Done column or names another "done" (`isDoneColumn` is by name); `create_project` restores `activeProjectId`; handoff memories are not editable; resolving a conflict archives, never deletes. Timers a run created over MCP are tracked in main (`agent-task-timers.ts`) by their start instant (`start_task_timer` returns `startedAt`; `jaRodando` means the run does not own it) and stopped, with the time saved, when the run ends and on app quit (`before-quit` waits up to 3 s). The stop goes through the internal renderer action `stop_run_timer` (not an MCP tool), which only stops the timer started at that instant, so a timer the user started or restarted is never touched. A start that lands after its run ended is stopped right away. The agent briefing tells the agent to time every task it works on. Out of scope on purpose: code paths, changing a table's currency, writing to another financial profile.
- **Memory** (below) is the only durable context the app keeps for agents.
- `skills.ts`, `web-fetch.ts`, `web-render.ts` and `code-files.ts` (above) are infrastructure that outlived the chat; their rules still hold.
- `modules/ai/evaluator.ts` and `eval/` (`npm run eval`, `eval:check`) are a leftover golden-trace harness for the retired tool loop. They stay until someone decides their fate; nothing in the app imports them.

### Agent-first architecture

This section is the architectural source of truth for executors. The target is a **single harness-backed code-agent thread**, never a generic provider/API chat beside it. Codex, Claude Code and OpenCode are selectable harnesses, not provider profiles. The common adapter/session contract, explicit capability matrix and migration rules live in [`docs/harness-chat-architecture.md`](docs/harness-chat-architecture.md). Its `unknown`/`unsupported` states are load-bearing: do not claim authentication, model selection, session resume, permissions or local-instruction support that a specific installed CLI has not actually exposed.

**Responsibilities.** The user talks to the CLI in the Fleet terminal; Sagyou does not coordinate through another model. Electron main owns the PTY, worktree, MCP broker, credentials, process termination and patch delivery. Fleet/xterm renders the PTY and forwards only validated input/resize; the renderer never spawns a process. The user owns the final delivery decision. There is no batch transport: ANSI, cursor state, paste, Ctrl+C and grid resize are raw terminal behavior over that restricted PTY IPC. The Windows manual acceptance script is `docs/agent-terminal-manual-test.md`.

The executor-neutral infrastructure is shared by the supported CLI executors: `agent-session.ts` owns run/reservation lifetime, `agent-pty.ts` owns interactive terminal creation, `agent-worktree.ts` owns isolated checkout lifecycle, `agent-diff.ts` captures/reviews the final patch, `agent-delivery.ts` serializes its application, and `agent-mcp-session.ts` grants/injects/revokes the scoped data bridge. Executor adapters (`harness-adapter.ts`) depend inward on these contracts. Approval, isolation and delivery semantics stay in the shared modules, not in executor-specific conditionals. The former native model loop (`code-agent.ts`), its ai-jail sandbox wrapper and the OpenAI client no longer exist in `src/main`.

**Boundaries.** Every executor run starts in its own detached Git worktree, including the first and only run for a project; no executor writes the original tree. Fleet asks for the session scope at creation, independently of the sidebar selection. A general session has no project or authorised code root: main ignores renderer paths and creates `userData/general-agent-workspace` as its private source for a detached worktree. Project sessions still require a selected, authorised code root. The CLI accesses the worktree filesystem directly. For Sagyou application data — projects, tasks, memories, finance and every future domain — the local scoped MCP server is the **only** bridge. PTY is a terminal transport, not a data API. Never expose SQLite, internal IPC, `loadData()`, a Zustand snapshot or a parallel ad-hoc bridge to the CLI. MCP credentials use 256 bits of entropy, are run-scoped, capture the chosen default project, financial profile and tool permissions at launch, expire after at most two hours and are revoked on every terminal path. The broker verifies that capability on every call and never logs or renders the token. MCP writes are serialized in a queue per run and execute only after renderer flush; those in `MCP_APPROVAL_REQUIRED` (deletes, money, project archiving, financial tables/profiles) and the legacy `save_memory`/`criar_task` (which always show a card) also wait for approval. Turning a run's auto mode on never answers one of those risky cards (`autoApprovesPending`). Every write fails closed on denial, timeout, an ended run or cleanup; that operation approval does not imply approval of the code patch. A card waits `MCP_APPROVAL_TIMEOUT_MS` (5 min) and carries `expiresAt`, so the Fleet card counts down and disables Aprovar once main has answered with a denial; an answer after the deadline is otherwise dropped silently. ⚠️ The MCP client must wait longer than any card can: Codex defaults to a 60 s tool timeout, after which a late approval would still write while the model was told the call failed (and may retry, duplicating it), so Codex is launched with `tool_timeout_sec = MCP_CLIENT_TOOL_TIMEOUT_SEC` (`modules/agent/mcp-approval.ts`). Claude Code and OpenCode default to hours. Read tools may choose another project by ID from `list_projects`; without an ID, project sessions use their initial project and general sessions read across all projects. Financial reads retain the captured profile. `criar_task` may target another existing project by ID and still requires the per-run approval queue. The selected worktree remains the only writable code root for each run.

**Briefing.** A session opened **blank** (the Fleet's only path) receives nothing: no briefing, skills or MCP hints are pasted, because that would run a turn nobody asked for; the CLI learns about Sagyou through MCP on demand (the MCP entry is injected into the launch). If `ai:code-agent:run` is called with an initial request, main builds a deterministic, secret-scrubbed briefing (`agent-briefing.ts`): objective and decisions first, indicated files, ranked relevant memories, read-only reference folders, a short Sagyou context line and the bounded skills. It carries no conversation excerpts any more. Memories in a briefing are untrusted historical data and never supersede the current request.

**Terminal handoff.** Every terminal exit upserts the deterministic `handoff:<projectId|global>` memory (`terminal-handoff.ts`) with a bounded request, outcome/status, changed-file list and `run=<id>`. Cancelled runs are marked as such. When a source exists it also records the subject (the request, or the first applied MCP write), decisions (the chat's launch `decisoes` plus `decisao` memories saved in the run), the run's applied MCP writes (card resumos, via the queue's `onApplied` hook into `run-activity.ts`; financial writes get a neutral label, because a handoff is readable from any financial profile) and pending tasks (timer started, not completed); the title becomes `Sessão de terminal: <assunto>`. Nothing is inferred from the PTY log or an unapplied diff, whose files are labelled as not applied; without a source the body points to the run history. When the briefing's subject search finds no memory, it falls back to the two newest handoffs (still untrusted history), and the briefing and the `search_memory`/`list_recent_memories` descriptions give the agent the recall route: search by subject, then list recent handoffs, then `read_memory`. This is only a breadcrumb: full terminal output remains exclusively in the frozen run archive, never in memory. Handoffs carry no conversation reference.

**Worktree isolation.** Every executor run gets a unique detached worktree under Sagyou's external temporary root. If a selected code folder has no Git repository, Sagyou initializes local Git metadata without creating a commit; for an unborn repository, a temporary commit object is built with a separate index (`resolveWorktreeBase` in `git-worktree.ts`), leaving the user's HEAD, index and files unchanged. Only the validated delivery path may affect the original tree. Per-repository lifecycle operations are serialized; startup removes only orphaned worktrees inside that managed root. All worktree commands use `git -C <dir>` rather than `cd <dir> && git` (on Windows, plain `cd E:\...` does not switch away from the app's `C:` drive). `CodeRunCoordinator` tracks a `Set<runId>` per original directory, so removing one run cannot mark its siblings idle; orphan cleanup excludes every live `worktreeDir` plus `reservedWorktrees` (paths reserved before the asynchronous `git worktree add` finishes). Deliveries are serialized per original directory with a unique `.sagyou-wt-patch-<runId>.diff`; conflicting patches stay archived as `merge_failed`.

**Lifecycle / success.** (1) The user picks scope and harness in the Fleet. (2) Main creates/reserves the worktree and MCP capability before starting the PTY in that worktree. (3) The harness edits and tests there, consulting Sagyou only via MCP. Codex's stdio MCP entry must whitelist `SAGYOU_MCP_PORT` and `SAGYOU_MCP_TOKEN` in `env_vars`; keep their values out of args and files. (4) Normal exit closes the PTY, revokes MCP, validates the complete changed-path set and freezes the log/diff; paths are normalized, case-aware on Windows, and both sides of renames plus symlinks are checked against the frozen file/root scope. One violation rejects the whole patch and is listed in Fleet; the original tree is still untouched. Interactive sessions archive their diff and exit without waiting for approval or applying it to the original tree. For non-interactive runs, one explicit manual approval applies the patch serially and records delivery. Auto-approve never covers final delivery. Immediately before applying, `git apply --check` validates the exact binary-capable patch without relaxed whitespace/context matching; a user edit made during review blocks delivery. Rejection records no delivery. Cleanup happens only after preserving the artifact needed for review/audit.

**Lifecycle / failure.** Worktree, MCP or PTY startup failure aborts before an executor runs. Crash, timeout or window/session teardown kills the child and revokes MCP. MCP failure is fail-closed: there is no SQLite/IPC/snapshot fallback. An out-of-scope path, invalid diff or apply conflict blocks delivery and archives the patch as failed for review. In an interactive session, normal CLI exit archives the diff without a pending approval or delivery; there is no separate renderer command to end or stop the PTY. Cleanup must be idempotent and must never remove another live/reserved worktree.

**Run archive (`agent-runs/`, `modules/agent/agent-runs.ts`).** One frozen record per finished run: `index.json` (metadata the picker lists) + one `<id>.json` with its log and diff, written once when the executor exits. ⚠️ **Never recompute the diff of an archived run** — it would measure today's tree and present the user's later edits as the agent's work (`CodeDiff` takes an optional `onRefresh` for that reason). `AgentRunMeta` is owned by the **session and project**, not a conversation: `sessionId` (the Fleet session that started it) and `projectId` (`null` for a general session). The old `convId` is kept, read and preserved so rows archived before the removal stay listable, but new runs write it as `null`; `runsForSession` also matches an old row (null `sessionId`) by its legacy `convId`. `runOwnership()` builds the ownership fields. `agent` is free text (the executor name; old rows without it read as `"codex"`). Runs are pruned by a 24h TTL (`RUN_TTL_MS`, applied lazily on every `loadRunIndex`), then `MAX_RUNS_PER_CONV` (20, per session) and `MAX_RUNS_TOTAL` (100).

## Data / Schema safety

The app persists state to a **SQLite database** (`kanban.db`) in `app.getPath('userData')`. There is **production data in the wild** — users have real tasks, habits, goals, and financial records stored on their machines.

Goals have an optional persisted `kind`: `completion` for a one-off objective or
`quantity` for accumulated progress. A missing value is deliberately read as
`quantity`, preserving every pre-feature goal even when its target is 1. Completion
goals keep the existing entries model (`target = 1`; completion adds one value-1
entry), so conversion preserves history and deleting that entry reopens the goal.
SQLite stores the value in nullable `goals.kind`; `migrateGoalKindColumn` adds the
column idempotently and does not backfill or guess a type.

Not everything lives in the DB. Also in `userData`:

The consolidated financial view must keep native totals separate by currency; a cross-currency equivalent is a live display-only calculation, never a persisted or historical total.
The selected financial month caps both balances at its end: the current balance stops at the current local day if that month has not ended, while the projected balance includes registered future transactions through the selected month. Financial goal progress uses that selected month (or today within the current month), capped at the goal deadline; future-only attainment is labeled as projected. In the consolidated view, exclude linked mirror transactions from both balances and keep native currencies separate.
Monthly yield summary transactions use the first day of their month so they affect the current balance immediately. On load and backup import, migrate only old last-day summaries matching the generated category and exact month/year description; record the date edit in the transaction audit and clear reconciliation via `applyFinancialTransactionEdit`.
Provider and actual balance are optional financial-table metadata. Old budgets and recurring transactions are unsupported features; their values survive in `legacyFinancialMetadata` through DB and backup round-trips, but are absent from the active model and Excel export. Do not remove this bridge without an explicit migration or an ordinary save could erase older data.

Financial tables belong to a `FinancialProfile`. `profileId` lives in table metadata, while profiles and the active profile are stored in SQLite `settings`. Missing legacy ids always migrate to the immutable `personal` profile (`Minhas finanças`). Filter every table picker, consolidated total, Dashboard financial summary, and the MCP financial read by the active profile; never create or retain a cross-profile transaction link.

The MCP read tools (`ler_tasks`, `ler_financeiro`, `ler_projeto`, `list_projects`) are bounded. Keep the list bounded and any completeness metadata (`total`, `truncado`) if adding domains; financial entities obey the captured profile, including direct ID lookup.
Excel export is deliberately global: its `Todas transações` sheet includes every profile, table and month, independent of the visible finance month. Keep exact decimal text alongside numeric money columns. Per-table transaction sheets duplicate those rows, so they are opt-in; when enabled, create only nonempty sheets with unique names. Omit `Detalhes financeiros` when it has no rows.
Custom finance categories live in optional `FinancialProfile.customCategories`, shared only by that profile's tables. Removing a suggestion does not rewrite historical transaction categories; used categories stay visible in pickers and filters.

### Remoção do chat genérico

The generic API chat, its history and its API connection were removed (spec `docs/specs/2026-10-24-remover-historico-chat.md`; user-facing description in `docs/data-migrations.md`). ⚠️ Breaking schema change — existing data was **deleted by design**. What the code does on the first open of the new version (`modules/ai/legacy-chat-removal.ts`, driven by `handlers/legacy-chat.ts` from `app.whenReady()` **before** `createWindow()`; a failure is logged and never stops the app from opening):

1. If `legacyChatRemovedAt` exists in `userData/legacy-chat-state.json`, do nothing. **A dev build (`is.dev`) skips the whole migration unless `SAGYOU_RUN_LEGACY_CHAT_REMOVAL=1`**: only the database has a dev suffix (`kanban-dev.db`), so everything else it deletes is the installed app's real data. An install that never had a chat (no file to delete, no retired key in `ai-config.json`) gets only the marker, with no snapshot and no notice. A snapshot recorded by an interrupted run is **reused**, not repeated, and its path is recorded before the first deletion.
2. **Snapshot first, by raw copy in main** (never through the renderer): `userData/backups/pre-remocao-chat-<timestamp>/` gets `ai-conversations.json`, `chat-images/`, `chat-files/` (whichever exist) and a consistent copy of `kanban.db` (`db.backup`). `ai-config.json` is **deliberately not copied** (it holds the keys). If any copy fails the half-written folder is removed and **nothing is deleted**; the next launch tries again.
3. Delete `ai-conversations.json`, `chat-images/`, `chat-files/`, `ai-usage-log.json`, `ai-run-metrics.json`.
4. Scrub memories (active **and** archived): `source_conversation_id` becomes null and the `(conversa completa: id=… — use ler_conversa…)` tail is cut from handoff bodies.
5. (No search rebuild here: the FTS index is derived and `getDb()` already rebuilds it from SQLite on every open, where conversations are no longer indexed. Rebuilding again made the first window wait for every document to be re-parsed.)
6. **Last**, strip the 14 retired keys from `ai-config.json` (`baseUrl`, `apiKey`, `model`, `providerProfiles`, `activeProviderProfileId`, `legacyProfileMigrated`, `chatProvider`, `modelComplex`, `maxSteps`, `inputPricePer1M`, `outputPricePer1M`, `timeoutMs`, `lastConversationId`, `codeAgent`), written atomically (`.tmp` + rename); everything else, unknown keys included, survives. An **unreadable `ai-config.json` is left untouched** (a warning is logged): it may still be recoverable. The keys go last because they are the one thing no snapshot can restore.
7. Write `legacyChatRemovedAt` (ISO time). Every step after the snapshot is idempotent and the marker is written only at the end, so an interrupted run resumes on the next launch.

`legacy-chat-state.json` also holds `legacyChatSnapshotDir` (the **first** snapshot's path; a retry that produces a second folder does not overwrite it, because the second one holds no conversations) and `legacyChatNoticeDismissedAt` (set by `legacy-chat:dismiss`; the notice keeps showing until then). ⚠️ **This state lives in its own file, not in SQLite `settings`, on purpose**: `persistAll` runs `DELETE FROM settings` on the first save of every session, which erased the marker and made the migration (and its `kanban.db` snapshot) repeat on every launch. A regression test pins the file (`handlers.test.ts`, `legacy-chat-state.test.ts`). The file is outside every backup; an unreadable one reads as empty.

⚠️ **The API keys are in no backup, so their loss is permanent.** The snapshot folder is raw files readable by hand, **not** a Sagyou backup: importing an old backup cannot bring the chat back, because import ignores `conversations`/`chatImages`. Never offer a "restore chat" path without a new spec. The memory column `source_conversation_id` stays in SQLite (no table rebuild) but is never read or written; `AiMemory.sourceConversationId` is always `null`.

### The backup bundles the physical files (v7)

A backup is a **single `.json`** (`backup:export`/`backup:import`, `version` 7; the validator accepts 1–7) that carries the binaries base64-encoded: `Backup.fileBlobs` (attachment bytes, keyed by `<id><ext>`) and `Backup.taskImages` (task-image bytes, `{id,ext,base64}`, keyed by the metadata on `tasks[].images`), plus `Backup.files` — the attachment **metadata**. It also carries `memories`. **It no longer carries `conversations` or `chatImages`**: export omits them and **import ignores both** from an older backup instead of failing (`backup-validation.ts`, `handlers/backup.ts`); `memories[].sourceConversationId` is dropped on the way in. A **legacy** backup with a task image's bytes inline as `dataUrl` is converted to a disk file on import (`importBackup`), the one place that still handles the pre-disk shape.

The split of responsibility is deliberate and load-bearing: **the bytes never cross IPC.** The renderer's `exportBackup` adds only the structured data + `files` metadata; the **main** `backup:export` handler reads the blobs off disk and injects them at write time. On import, **main** `backup:import` validates the envelope with `isValidBackup`, retains blobs in main and strips them from the payload returned to the renderer. The renderer forces a pre-import snapshot, then writes store and memories; it commits blobs only after those succeed. A failure at any stage restores the prior store and memories and surfaces an error rather than reporting a partial restore as successful. The renderer restores `files` metadata from the backup (falling back to local when the key is absent). `backup:auto-save` writes an atomic snapshot in `userData/backups/` on load and hourly thereafter, updating the day's file and retaining the seven newest snapshots; forced pre-import snapshots get a timestamped name. Keep this order: no restore may mutate files or data before validation and the pre-import snapshot succeed.

**`repairBackup` (`modules/files/backup-repair.ts`) runs before `isValidBackup` on both `backup:import` and `backup:auto-save`.** It exists because the validator once refused backups the app had exported itself, and the same state made every hourly snapshot fail silently: sprints/notes of a deleted project are dropped, a `projectId` holding a project's *name* (old data) is pointed back at its id when unambiguous, a goal linked to a deleted project loses only the link, a planner block linked to a deleted task or habit loses only the link, and a planner block/routine with end ≤ start ends at 23:59 (when it ended at `00:00`) or one minute after its start (a `23:59` start moves to `23:58`). Anything else is left for the validator to refuse. **`backup:auto-save` writes the state unrepaired**: the repair only decides whether it is restorable (import repairs it again), so a restore point never loses what was in the database. ⚠️ A new validation rule that existing data can violate needs a matching repair, or it locks users out of their own backups. `deleteProject` removes the project's sprints and canvas notes and unlinks its goals; deleting a task, project or habit unlinks planner blocks (`unlinkTimeBlocks`); the routine forms refuse end ≤ start like the block form. So the app no longer produces those leftovers.

`isValidBackup` is intentionally stricter than an envelope check: it rejects duplicate IDs per collection, malformed persisted dates/timestamps, invalid planner times/days, broken task→project→column references, and broken planner task/habit references before any renderer state or blob is touched. New validation must preserve explicitly supported legacy omissions, rather than treating an additive field from a new version as mandatory in an old backup.

Backup blob export is an asynchronous cooperative job: `handlers/backup.ts` yields between files, streams `backup:export-progress` to the renderer, and honors `backup:export:cancel`. Keep expensive file reads/base64 conversion off the synchronous dialog path; manual export must remain cancellable and show progress.

⚠️ **The ids/exts in a backup are untrusted** (a user can hand-edit the file), and a restore joins them onto `files/`/`task-images/` to write — so `safeAttachmentName` (pure, tested in `backup-files.test.ts`; also guards `task:images:*` at runtime) + a `startsWith(dir + sep)` re-check gate every write; a traversal id (`../../ai-config.json`) writes nothing. Same rule as the rest of the format: an **absent** `files`/`fileBlobs` key (an old backup) restores nothing and leaves local files untouched, never wipes them. The one accepted cost of base64-in-JSON: a very large attachment set makes a big backup held in memory as one string — fine for this cold, on-demand path.

- **Never remove or rename fields** on existing types without a migration or backward-compatible fallback (e.g. optional field with a default on load).
- **Never change the shape of persisted arrays or objects** in a breaking way (reordering, nesting, type changes).
- Adding new optional fields is safe — the store hydrates with `??` defaults and missing keys are silently ignored.

### Code path selection is a two-field pair

`Project.activeCodePathIds: string[]` is the source of truth for which code paths the agents may use. An **empty selection is a legitimate state** — never backfill it from the remaining paths, e.g. on remove. Auto-selecting a folder the user didn't pick silently hands an agent a directory to work in. The legacy singular `Project.activeCodePathId` is **still written**, mirroring `activeCodePathIds[0]`, so older app versions and old backups keep resolving a selection. Go through `activeCodePathIds()` / `withActiveCodePaths()` in `store/normalization.ts` — never set either field by hand, or the two drift apart. `normalizeProject` on load migrates legacy singular data and drops ids whose code path no longer exists.

The `project_code_paths` SQLite table needed no migration: `active` was already a per-row flag, so multiple selected rows just means multiple `1`s. `persistAll` writes every selected id; the loader collects all `active` rows.

- **Always warn explicitly** before making any change that could corrupt or lose existing data on load (e.g. changing a field from `string` to `string[]`, removing a required field, changing an ID scheme). Flag it with: _"⚠️ Breaking schema change — existing data may be affected."_

### Timers are a collection (multi-timer)

`useKanbanStore.activeTimers: ActiveTimer[]` — at most one per task (logical key = `taskId`) — replaces the old single `activeTimer`, so several tasks can be timed at once. `startTimer(taskId)` **adds** a timer and no-ops if one already runs for that task (it must not reset the clock) and **does not stop other tasks' timers**; `stopTimer(taskId)` credits that one task's elapsed time and removes only its timer. The Done-boundary auto-stop in `moveTask`/`updateTask` stops just the affected task.

Same **legacy-mirror** pattern as `activeCodePathId`: the persisted payload carries `activeTimers` **and** `activeTimer = activeTimers[0] ?? null`, and the SQLite `settings` table holds both keys (`main/store.ts` `writeTimers` writes/clears both from one place; `loadData` prefers `activeTimers`, else wraps the legacy `activeTimer`). `normalizeTimers` in `store/normalization.ts` migrates a legacy single object to the array on load; `loadData` then **commits elapsed time for every running timer in a loop**. Timers do **not** ride the backup (only the DB `settings` do). ⚠️ It is a schema change all the same — the collection shape and the mirror must both be kept, or an older app version stops resolving a running timer.

### Monetary fields are decimal strings

`FinancialTransaction.amount`, `FinancialTransaction.details[].amount`, `FinancialGoal.targetAmount`, `FinancialDebt.originalAmount`, `FinancialDebt.remainingAmount`, and `ShoppingItem.price` are stored **in memory and in backups/JSON as canonical decimal strings** (e.g. `"1500.5"`), not numbers. All money arithmetic goes through `decimal.js` — use the `D()` helper and `Decimal` methods (`.plus/.minus/.times/.div`) in `components/financial/shared.ts`; only convert to `number` for display geometry (bar widths, percentages). `qty` stays a `number` (it's a quantity, not currency).

Debt payments are atomic in the financial slice: every partial payment reduces `remainingAmount` and writes one expense transaction with `debtId` in the same table. Do not edit a debt-payment transaction independently; deleting it restores the balance, while deleting the debt only unlinks the historical transactions.

Planner writes must validate real 24-hour `HH:MM` values and require `endTime > startTime`.

Window close is a renderer/main handshake: main prevents the first close event, renderer flushes Zustand state, then explicitly acknowledges through IPC. Do not replace it with an async `beforeunload` handler — Electron does not wait for that IPC. The 10-second fallback exists only to recover from a dead renderer.

`App` wraps its active workspace in `ViewErrorBoundary`. Keep this boundary around new primary views: it contains render failures to that area, offers retry, and resets when navigating to another view so the application shell stays usable.

`ModalBase` is the accessibility contract for shared modals: it supplies dialog semantics, initial focus, Tab trapping, Escape-to-close and focus restoration. Board drag-and-drop also includes dnd-kit's `KeyboardSensor` with `sortableKeyboardCoordinates`; do not remove it when changing sensors.

Formatting never changes stored amounts. JPY summaries use dot grouping and round to whole yen; existing fractional yen remain visible in edit fields so historical data is not silently changed. Edit fields group thousands (BRL and JPY with dots, USD with commas) and retain any stored fraction beyond the usual currency precision. Yen input treats `1.000` as one thousand; `formatAmountInput` adds a trailing zero to an ambiguous historical fraction such as `1.123` before editing so parsing can round-trip its canonical value. Pass the table currency to `parseDecimalInput` for every monetary edit (including goals, details, shopping prices and yields); quantity inputs keep the local numeric default. `formatAmountInput` and parsing must round-trip canonical values before an unchanged field blurs, or a display-only change can overwrite real money.

On the Home dashboard, selecting an individual financial table displays its native amounts in that table's currency. Exchange-rate conversion to BRL is only for the Consolidado selection; never pair a converted BRL amount with a selected table's currency symbol. The opening balance includes transactions through the current local date, even when the last posted transaction is from an earlier month; future-dated transactions do not contribute.

An invoice detail may carry `linkedTransactionId` pointing to its mirror transaction in another
financial table. This is deliberately different from the legacy transaction-to-transaction link:
the detail link keeps the whole invoice in consolidated totals and omits the mirror, while the
legacy link keeps the child and omits its parent. Detail links require equal amounts and currencies.

Financial documentation stays on `FinancialTransaction`: `receiptFileIds` point to shared `files/`
blobs (metadata and bytes are already included in backups), while `source`, `bankReference`
and `counterparty` identify the operation in an external statement. Deleting a library file must
remove its ID from transaction references. New transactions receive `createdAt`; old records keep
it absent because their creation time is unknown. `applyFinancialTransactionEdit` appends field
changes to `audit` and updates `updatedAt`; a change to amount, date, type or bank identity clears
`reconciledAt` so an old bank reconciliation cannot silently cover a corrected transaction.

Foreign-currency account transfers use `currencyTransferId`, separate from invoice mirrors and
legacy links. Pair only an expense and an income from different tables/currencies in the same
financial profile. Both original transactions remain in native cash-flow totals. The effective
rate is derived from their original decimal-string amounts. `currencyTransferFee` and its currency
are informational metadata on the pair; charge the fee as an expense transaction if it needs to
affect balances. The transaction's optional record fields persist in SQLite `record_metadata`,
added to existing databases by an idempotent migration; Excel includes documentation, audit and
a transfer-pair sheet.

- On load, `normalizeFinancialTable` migrates any legacy `number` values to canonical string via `moneyStr` — old data and old backups keep working.
- The SQLite columns for these fields are `TEXT` (`price`, `amount`, `target_amount`), storing decimal strings on disk. `qty` stays `REAL`. On insert, `moneyText()` in `main/store.ts` coerces number-or-string to a string.
- `migrateMoneyColumnsToText()` in `main/store.ts` upgrades existing databases: it detects the legacy `REAL` columns via `PRAGMA table_info` and rebuilds those three tables as `TEXT` (create `_new`, `CAST` copy, drop, rename — inside a transaction with foreign keys toggled off). Idempotent: skips tables already `TEXT`.

### Memory is a satellite table, written outside `persistAll`

The `memory` table (durable facts carried across sessions — decisions, tradeoffs, gotchas, per-session handoffs) lives in `kanban.db` but is **deliberately not part of the Zustand store or `persistAll`**. The reason is the touch path: `access_count`/`last_accessed_at` are bumped on reads (that's what feeds decay), and routing that through `saveData`'s full-replace would rewrite every table per bump. So memory has its **own targeted statements** in `store.ts` (`listMemories`, `memoriesForContext`, `getMemory`, `upsertMemory`, `touchMemories`, `archiveMemories`, `deleteMemory`) reached by dedicated `ai:memory:*` handlers — never `store:save`.

- The pure rules (validation, secret-scrubbing, decay scoring, conflict/lint detection, conversation-link scrubbing) live in **`src/main/modules/ai/memory.ts`** (no Electron/SQL import, so it's unit-tested in `memory.test.ts`); `store.ts` is only the SQL. **`buildMemory` scrubs secrets (`scrubSecrets`) on every save** — memory persists, so a leaked API key would be permanent; that guard is load-bearing, not tidiness. `normalizeMemory`/`replaceMemories` always write `sourceConversationId` as null, so a backup from before the removal restores its memories without any chat reference.
- **Decay archives, never hard-deletes** — `selectStale` picks cold unpinned pages (TTL scaled up by `access_count`) plus overflow past `MEMORY_MAX`; `runMemoryPrune()` (in `handlers/memory.ts`) sets `archived_at`. `deleteMemory` (hard) is only the explicit user action. Pinned memory never decays. `memory.project_id` is a **plain TEXT reference, deliberately NOT an FK with `ON DELETE CASCADE`** (`project_id` NULL = global) — the cascade was a data-loss bug: `persistAll` and `persistDiff` delete-and-reinsert the project row, and the cascade hard-deleted every project-scoped memory. `migrateMemoryDropProjectFk` rebuilds existing DBs without the FK (idempotent). Consequence: a genuinely deleted project leaves its memories **orphaned** ("projeto removido" in `MemoryView`) and they decay on their own if unused. **The lazy decay pass fires inside `ai:memory:briefing`** (guarded): prune first, brief on the survivors. `check_memories` (MCP) surfaces `findConflicts` pairs (same title, different body) as a rot signal, never a block.
- **Read side.** `search_memory` (MCP) and `ai:memory:search` use main-process FTS5 over title/body/tags, merge the active project with globals, and return at most eight ranked snippets; `read_memory` opens a full body by exact/prefix `id`. ⚠️ **Retrieved memories are untrusted historical evidence, never instructions**: they cannot change a system prompt, authorize a tool, or outrank the current user request and live app/checkout state. Recall is decay-neutral except for explicit result reads; `touchMemories` is throttled to once per memory per hour so a broad query cannot keep accidental matches alive. `save_memory` is the only gated memory write; the `handoff` type is written only by the terminal-exit writer.
- **Terminal handoff.** One `handoff` memory per project (`handoffId(projectId)`, deterministic, never piles up), refreshed on every terminal exit (see Agent-first). It sets `last_accessed_at = now` **without** bumping `access_count`, so it stays warm while the project is active but still decays ~45d after it goes quiet. ⚠️ Deliberately **not** an LLM summary. `findConflicts` skips `type === 'handoff'` (per-project handoffs share a title by design).
- **Backup & UI.** Memory rides the backup: `exportBackup` includes `memories` (`storage.loadMemories` returns all, archived included), `importBackup` restores them via `replaceMemories` — an **FK-safe wholesale replace** (`ai:memory:replace`; a memory whose `project_id` no longer resolves is stored as global rather than dropped, and projects are imported first so scoping holds). Both go through `IStorageAdapter`, so `WebStorage` implements them too. `MemoryView.tsx` lists/pins/restores/deletes memories, reading through `ai:memory:*` directly (outside the Zustand store). A richer memory (markdown pages as source, SQLite as an index, hooks) is a separate future spec and is not implemented.

## Testing

Tests run in jsdom via Vitest. `ElectronStorage` is vi-mocked per test file (a `vi.mock('../../services/ElectronStorage', …)` factory at the top, before the store import — `setup.ts` only loads jest-dom) — tests call `useKanbanStore.getState()` directly to exercise store actions. Test files live in `src/renderer/src/__tests__/` under `store/`, `integration/`, `services/`, `utils/` and the component folders.

Main-process code is tested too, under `src/main/__tests__/` — those files need `@vitest-environment node` (the suite defaults to jsdom). `handlers.test.ts` covers the real IPC handlers: it mocks `electron` just enough for `app.whenReady()` to run (that's what registers them) and captures `ipcMain.handle`, including the startup order of the legacy-chat removal. `memory.ts`, `agent-runs.ts`, `legacy-chat-removal.ts` (injected effects, real temp dir), `code-files.ts` and the web modules are tested directly as plain modules. `better-sqlite3` is built for Electron's ABI and does not load under vitest, so SQL in `store.ts` (e.g. `scrubMemoryConversationLinks`) is verified in the app, not in unit tests.

Every bug fix needs a regression test that reproduces the prior failure and
asserts the corrected behavior. A test that only mirrors the implementation
doesn't protect against the bug returning.

⚠️ When testing path confinement, the file outside the root **must actually exist**. A test using `../nope.txt` passes whether or not the confinement works, because the handler rejects the missing file anyway — it proves nothing. `handlers.test.ts` puts the root inside a container with a real `secret.txt` sibling for this reason.

The `coverage/` directory is generated output — do not commit it.

GitHub Actions runs typecheck, the full test suite and coverage on every pull request and branch push. Coverage includes both `src/main/` and the renderer; it is an observability report, not a percentage gate, so important main-process paths can be improved without rewarding superficial tests. The repository has historical lint debt, therefore PR CI filters ESLint through the diff and makes errors introduced in changed context blocks blocking; unrelated legacy violations stay visible without masking a new regression.
