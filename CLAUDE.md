## Architecture

The app is a frameless Electron window split into three processes:

**Main** (`src/main/`)
- `index.ts` — creates the BrowserWindow, registers IPC handlers for `window:*`, `store:*`, `backup:*`, `files:*`, `excel:*`, `ai:*`. Also proxies all AI provider calls (keeps the API key out of the renderer and sidesteps CORS), spawns the external code agent, and serves read-only source access to the assistant.
- `chat-images.ts` — images pasted/dropped into the chat, stored as **files** under `userData/chat-images/`. **The transcript keeps ids only, never base64**: `ai-conversations.json` is re-read and rewritten whole on every autosave *and* every keystroke of the history search, so inlined screenshots would drag both down permanently. `ChatMessage.imageIds` is additive (old files simply lack it); the bytes load into `imageData` on demand, and a missing file degrades to "[imagem indisponível]" with the turn's text intact.
  - `isImageFileName()` is a **security guard, not a tidiness check**: the id comes back from the renderer to read or delete a file, so it is a path in disguise (`../../ai-config.json`). `decodeDataUrl()` likewise refuses non-image data URLs rather than writing whatever it's handed under an image's name.
  - `utils/images.ts` downscales to `MAX_IMAGE_EDGE` (1024) before saving, kept as PNG — these are screenshots and JPEG artefacts around small text are what make them unreadable to a vision model. **The agent resends the whole conversation every step**, so an image in the history is re-uploaded on each one — up to `AUTO_MAX_STEPS` (100) times in automatic mode, more if the user raises `maxSteps`.
  - Vision turns use `ApiMessage.content` as a `ContentPart[]`; text-only turns stay a plain string, since not every OpenAI-compatible provider accepts the array shape. That union is **wire-only** and never reaches disk. `contentText()` flattens either form.
  - Deleting a conversation deletes its images (`AIView.confirmDeleteConversation`), as does removing an attachment before sending or hitting "Nova" — nothing else references those files.
- `task-templates.ts` — the rules behind `ai:templates:*` (named prompt templates for Gerar Tasks, stored in `ai-templates.json`; the picked one is `AIConfig.taskTemplateId`). **`AI_TASK_PROMPT_TEMPLATE` stays in code as the fallback and is never stored** — `activeTemplateBody` in `AIView` falls back to it whenever the selection can't be honoured (nothing picked, or the picked template was deleted in another window), so Gerar Tasks can't be broken by a dangling id or a hand-edited file. "Padrão" is always in the picker and can't be deleted. `normalizeTemplates()` drops unusable rows on load for the same reason, `saveTemplate()` refuses a blank name/body and duplicate names (indistinguishable in a dropdown), and a new template starts pre-filled with the built-in so it still asks for the `tasks` JSON the importer needs. `Project` is deliberately untouched.
  - Note: the Sidebar's "Copiar tudo" still copies `AI_TASK_PROMPT_TEMPLATE` — it's a format reference for pasting into another LLM, not the in-app generation prompt.
- `web-fetch.ts` — backs `ai:web:fetch`: native `fetch`, 15s `AbortController`, response capped at `MAX_CONTENT_CHARS` (8000), returning `{ content, url, truncated }` or `{ error }` (`url` is the **final** one, after redirects).
  - ⚠️ **The URL comes from the model, so it is untrusted.** Once the assistant can read pages, a fetched page can tell it what to fetch next (prompt injection) — and this app runs on the user's own machine, where "the network" means their dev servers, NAS and router. So: **http(s) only** (`file:` would read the disk), **private/loopback/link-local/metadata hosts blocked** (incl. `::ffff:127.0.0.1` and `169.254.169.254`), and **redirects are followed by hand** with the same policy re-applied to every hop — `redirect: 'follow'` would let a public URL 302 straight into all of it. Entry URL and every hop go through one `validate`; no path is exempt.
  - **Embedded credentials are refused** (`http://user:senha@host/`), on entry and on every hop. Read off `url.username`/`url.password`, **never off the string** — `@` is legal in a path or query (`http://example.com/?x=a@b` has no userinfo), so a string test for '@' refuses ordinary URLs; and `http://:senha@host/` is userinfo with an empty username, hence both fields. This is depth, not a live bypass: `isPrivateHost(url.hostname)` already resolves `http://evil.com@127.0.0.1/` to 127.0.0.1 correctly. The reasons it goes anyway: forwarding credentials the model picked up off a page is a decision nobody made, and `http://google.com@evil.com/` reads as google.com in the `FetchOk.url` shown back to the user.
  - **The parser is the sanitiser, and the only one.** `new URL()` implements WHATWG, which strips ASCII tab/newline/CR *before* parsing — so `http://exa\nmple.com` is example.com, a CRLF meant for header injection lands percent-encoded and inert inside the path, and `.trim()` covers the rest. ⚠️ **Never add a hand-rolled cleaning pass in front of it** — no character stripping, no HTML-entity decoding. The invariant holding this together is that **the URL checked is the object fetched**: `fetchWeb` validates a `URL` and hands that same `URL` to `fetch`, so nothing re-parses a string and reaches a different host. A text pre-pass breaks exactly that — what it emits is what gets fetched, and it is not what was checked. HTML entities are a different encoding layer besides (URLs are percent-encoded); decoding `?a=1&amp;b=2` to `?a=1&b=2` silently fetches another query. All of this is pinned by tests, including one that fails if someone implements "reject URLs containing @" literally.
  - **Fetches are paced by waiting, not refusing** (`createRateLimiter`, `RATE_LIMIT_MAX` 10 per `RATE_WINDOW_MS` 60s, sliding). `buscar_na_web` needs no approval and **nothing caps tool calls per step** — only steps, at 50 — so an accidental loop can hammer a site from the user's own IP. It delays rather than errors because **the caller is a language model and a model cannot sleep**: "try again in 42s" reaches something whose only moves are to retry at once and fail, or give up, so a refusal mid-run tends to burn the remaining steps and answer nothing. Measured on a simulated clock: 3 and 10 pages wait **zero** (the burst allowance is what keeps ordinary use free), 12 pages cost one 60s wait, a 100-page runaway is throttled to ~9 min and still completes. `MAX_QUEUE_WAIT_MS` (2 windows) refuses only a hopeless queue — unreachable for a *sequential* caller, which the agent is, so it is a valve for concurrent pile-ups, not the protection; the throttling is. Its message asks the model to answer with what it has, never to wait.
    - ⚠️ **The slot is acquired before the `AbortController` timer starts.** `timeoutMs` is the page's budget to respond, not the queue's — start the timer first and a queued fetch aborts for "not responding" before it was ever sent, more surely the busier things get. A test pins this.
    - One slot per **logical fetch**, not per hop (a redirect chain is capped at `MAX_REDIRECTS`), and junk URLs are rejected on shape **without** spending a slot.
    - ⚠️ Known consequence: a queued fetch blocks inside the tool for up to a window, and `shouldAbort` is only checked **between steps** — so "Parar" can take up to ~60s to land during a >10/min burst (it was ~15s, the fetch timeout). Fixing that needs a cancellation path from renderer to main, which does not exist.
    - The limiter is **process-wide module state**, so tests must inject their own (`FetchDeps.limiter`) or they spend each other's slots and then queue for a minute.
  - **The request carries nothing of the user's**, and that is pinned by tests rather than asserted by a comment. This is a page the *model* chose, fetched from the user's machine and IP; it must not look like the user visiting a site. Measured against a real server, exactly this goes out: `host`, `connection`, `accept`, `accept-language: *`, `accept-encoding`, `sec-fetch-mode`, `user-agent: node` — no cookie (a `Set-Cookie` is never echoed to the next request), no `authorization`, no `referer`, across redirects too. The tests matter because the guarantee is a property of the **runtime, not of this file**: a Node release with a cookie jar, a refactor onto Electron's `net.fetch` (session-backed, so real cookies), or one added header would each pass review in silence. One test fails on any header outside the known set.
    - ⚠️ **`mode` and `credentials` are both inert in Node** — measured: `mode: 'no-cors'` still returns a `basic` response with its body, and even `credentials: 'include'` sends no cookie, because there is no jar. So `credentials: 'omit'` at the call site is **declarative, not load-bearing**; it is kept as intent and because it goes live if the client underneath ever stops being Node's fetch. Don't let a comment claim either one is protecting anything here.
    - Don't add `mode: 'no-cors'` (buys nothing in Node; would return an *opaque*, empty response in a browser), don't brand the user-agent (it tells every site the model visits which app the user runs — the opposite of the goal), and don't drop it (many servers 403 a request without one).
  - The cap is applied **while reading**, not after: `res.text()` would pull a multi-gigabyte response into memory and only then slice it to 8000 chars. Non-textual content-types are refused rather than handed to the model as bytes.
  - Not covered: **DNS rebinding** (a public name that resolves to 127.0.0.1) — that needs resolution plus a pinning agent. Literal IPs and `.local`/`.internal` are.
- `web-render.ts` — the **JS-capable sibling** of `web-fetch`, reached via `ai:web:fetch` with `render: true` (the `renderizar_js` tool arg): SPA pages that draw themselves with JavaScript (`openai.com/pricing`) come back as text via a **headless render**. Uses Electron's **already-bundled Chromium through a hidden `BrowserWindow`** — no second browser binary, and `session.webRequest` gives request interception natively (`playwright-core` is a dependency but **unused** — this path replaced it; it ships no browser anyway).
  - ⚠️ **A browser is a far larger SSRF surface than `fetch`, and closing it is the whole point of this file.** It runs the page's JS and loads every subresource (img, script, xhr, `fetch`, WebSocket), and **none of those go through `fetchWeb`'s by-hand redirect check**. On a machine where "the network" is the user's own LAN, an unguarded browser is a straight SSRF (`<img src="http://169.254.169.254/…">`, `fetch('http://127.0.0.1/admin')`). So **every request — main document and every subresource — is run through the same `checkUrl` policy** (`shouldCancelRequest`) via `session.webRequest.onBeforeRequest` and cancelled if refused; the main frame is additionally guarded on `will-navigate`/`will-redirect`. The context is an **ephemeral in-memory session** (no cookie jar, cleared after), `sandbox` on, no node integration, no preload, images off, popups denied, and WebRTC's non-proxied UDP disabled so a page can't probe the LAN off-HTTP. The user-agent is scrubbed to plain Chrome (`plainChromeUA`) — no app identity leaked, but not `node` either, or SPAs bot-block.
  - Paced by the **same `defaultLimiter`** as `fetchWeb` (now exported), so fetches and renders share one per-machine budget rather than a bucket each.
  - **What's tested vs. not:** the pieces carrying the security/privacy decisions are pure and pinned in `web-render.test.ts` — `shouldCancelRequest` (cancels exactly what `fetch` refuses) and `plainChromeUA`. The `BrowserWindow` orchestration itself **can't run under vitest** (needs the Electron runtime) — it must be **verified in-app**: a real SPA returns text, and `renderizar_js` on `http://127.0.0.1` is refused.
  - ⚠️ **Residual risks, documented not hidden** (a real engine can't fully close them): **DNS rebinding** (same literal-host gap as `web-fetch`), and a **subresource redirect** to a private host, which relies on `onBeforeRequest` re-firing for the new URL. Don't claim this is as airtight as the `fetch` path.
- `code-files.ts` — `confineToRoot()` + `walkFiles()`, backing the `ai:code:*` handlers. **Async on purpose, and it must stay that way**: these run on the main process's event loop, which also serves IPC and the window controls. Measured on a large tree, the sync version starved the loop for the walk's full duration (~22ms cached / ~73ms cold to the 3000-file cap) and `ai:code:search`'s `readFileSync` loop added ~640ms on top; awaiting `readdir`/`readFile` keeps the total the same but drops the longest stall to <1ms. A `worker_thread` would buy nothing here — the work is IO-bound, so libuv's pool already keeps it off the main thread. `confineToRoot` is the only barrier between the assistant and the rest of the disk (note `base + sep`, or `/project-evil` passes as a child of `/project`); it's tested in `src/main/__tests__/code-files.test.ts`.
  - **Scoped reading lives here too** (`detectSymbols`/`extractSymbol`/`extractLines`, pure and tested): they let `ler_arquivo` return one function or a line range instead of a 20k window paged five times — a whole file is resent every later step, so reading it to answer a question about one symbol is a compounding tax. All **regex/brace-matching best-effort, not an AST** on purpose (an AST would need a language-aware toolchain per file type; the model tolerates an imperfect slice far better than main tolerates that dependency). `extractSymbol` takes the first *declaration-looking* line for the name — a bare call site won't match, but a same-named field might — and its brace counter doesn't understand braces in strings/comments; `detectSymbols` is anchored at column 0, so it maps top-level/exported declarations only, never a nested `const`. `ai:code:read` uses them: `scope: { symbol?, lineStart?, lineEnd? }` (its optional 5th arg) wins over the char-window paging, and a big file's first page carries `simbolos` (the map) so the model can re-read just the symbol it needs — but only when `truncated`, since on a small file returned whole the map is redundant tokens.
- **The manual `tool_calls` assembly in `ai:chat:stream` is deliberate — don't "simplify" it.** `client.chat.completions.stream(...).finalChatCompletion()` does assemble deltas, usage and tool_calls for you, but its finalizer hard-throws `OpenAIError: missing role for choice 0` when a delta carries no `role`. Real OpenAI always sends one; an OpenAI-compatible server (local llama.cpp/Ollama/LM Studio, proxies) need not, and this app points at any endpoint. Verified against a mock provider: on role-less deltas the SDK helper throws — *after* the answer has already streamed — while the hand-rolled loop returns the tool call fine. (`stream.toReadableStream()` assembles nothing; it returns raw SSE bytes.) The loop trades ~20 lines for provider tolerance, which is the whole point of the feature.
- `openai-client.ts` — also owns `requestOptions(config.timeoutMs)`, passed to **every** model call (`ai:chat`, `ai:chat:stream` incl. its no-`stream_options` fallback, `ai:models`). Two things it fixes, both verified against a local server:
  - **`timeout`** — the SDK's own default is **10 minutes**, i.e. a hang. Defaults to 60s (`AIConfig.timeoutMs`, clamped 5s–600s; ≤0 or nonsense falls back). Safe to keep short because the SDK clears its timer when the response *headers* land, so this bounds **time-to-first-response and does not truncate a long generation** — a 2s stream completes fine under a 500ms timeout. A timeout surfaces as `APIConnectionTimeoutError` with **no status**, so `isRetryable(undefined)` retries it.
  - **`maxRetries: 0`** — load-bearing. The SDK retries twice by default, *underneath* the agent's own retry loop: measured, one answer fired **12 HTTP requests** (3 × 4), each able to burn the full timeout. Retry policy belongs to `callModelResilient` alone (it classifies status, backs off, reports to the user, and honours Stop).
- `openai-client.ts` — `getOpenAIClient(baseURL, apiKey)` reuses the SDK client across calls. **Keyed on the endpoint + key, not a true singleton**: both are editable at runtime and a request may override them, so a client cached past a config change would keep using the old endpoint/credentials. This is a de-duplication of the three old call sites, **not a speed-up** — the client holds no socket, agent or pool (connection reuse is the process-wide fetch dispatcher's job) and construction measures ~10µs against a ~1s call. Tests must run under `@vitest-environment node`: the SDK refuses to construct under a browser-like global, and the suite defaults to jsdom.
- `store.ts` — persists state to a **SQLite database** (`better-sqlite3`) at `app.getPath('userData')/kanban.db` (`kanban-dev.db` in dev). Opened in WAL mode with foreign keys on. Each save is a full replace inside a transaction (`persistAll` deletes children→parents, then re-inserts). One-time `migrateFromJson()` runs on first boot: if the legacy `kanban-data.json` exists and the DB is empty, it imports it and renames the file to `.migrated`. The `kanban-data.json` format now only survives as the backup/export shape (produced in the renderer), **not** as the storage format.

**Preload** (`src/preload/index.ts`)
- Bridges IPC to the renderer via `contextBridge`, exposing `window.electronAPI` (typed in `index.d.ts`)

**Renderer** (`src/renderer/src/`)
- Single-page React app. Entry point is `main.tsx` → `App.tsx`
- All state lives in one Zustand store: `store/kanban.ts`
- `App.tsx` owns all modal state and UI event handlers, passing them as props down to views and modals

### State layer

`store/kanban.ts` exports `useKanbanStore` (Zustand). Every mutation calls `_persist()` internally, which serializes the full state and calls `storage.save()` — the payload is sent over IPC and written to SQLite by the main process (see Main above).

Storage is injected via `IStorageAdapter` (`services/StorageAdapter.ts`). In production, `ElectronStorage` is used (calls `window.electronAPI`). `WebStorage` is a parallel `localStorage`-backed implementation kept for an eventual browser build — it is not wired up in the app, but it must keep satisfying `IStorageAdapter`, so a change to that interface means changing both adapters. In tests, `ElectronStorage` is vi-mocked in `__tests__/setup.ts`.

AI chat history is **not** part of the main store — it lives in its own file and is reached through `loadConversations()` / `saveConversations()` on the adapter, which backup export/import calls separately.

The **agent run** has its own store as well (`store/aiRun.ts`), for the same reason it isn't component state: it has to outlive both `AIView`'s mount and any one view. It is deliberately not part of `useKanbanStore` — it persists to `ai-conversations.json`, not to the DB, and nothing in the kanban state depends on it. See AI assistant below.

`loadData` and `importBackup` normalize every incoming `FinancialTable` through `normalizeList` — this fills missing arrays, defaults the currency, and **migrates monetary fields from legacy `number` to canonical decimal string** (see Data / Schema safety). Do the same for any new load path.

Soft deletes use a `Tombstone[]` array. On `importBackup`, all local state is replaced wholesale by the backup file — no merge. The helper functions `mergeEntities`, `mergeSprints`, `mergeHabits`, and `mergeTombstones` remain in `store/kanban.ts` but are unused.

### Views

`App.tsx` renders one view at a time based on `activeView` state:

| View | Component | Notes |
|---|---|---|
| `board` | `Board.tsx` | dnd-kit drag-and-drop across columns |
| `canvas` | `CanvasView.tsx` | free-form sticky notes with task links |
| `files` | `FilesView.tsx` | file attachments, optionally scoped to a project |
| `done` | `DoneView.tsx` | tasks in any column named "done" |
| `goals` | `GoalView.tsx` | progress goals with optional project link |
| `habits` | `HabitView.tsx` | daily habit tracker with streak |
| `financial` | `FinancialView.tsx` | shell over the tabs in `components/financial/` — shopping lists, transactions, financial goals, analytics |
| `upcoming` | `UpcomingView.tsx` | tasks with due dates |
| `reports` | `ReportsView.tsx` | productivity overview |
| `ai` | `AIView.tsx` | chat with the assistant (see AI assistant below) |

`conversation-search.ts` backs the history search box (`ai:conversations:search`). It runs in **main**, where the history file is already open — filtering in the renderer would mean shipping every message body over IPC per keystroke. It **strips accents** (a Portuguese app: "habito" must find "hábito"), **skips `status` messages** (the agent's own tool trace, so searching "App.tsx" surfaces chats that *discussed* it, not every chat that happened to read it), and returns a snippet for body matches so a hit explains itself. An empty term is not a filter — it returns the whole history, which is what the dropdown shows before anything is typed. `refreshConversations()` always goes through search via `historyQueryRef`, or the debounced autosave would drop the user's filter mid-typing.

**The run is not AIView's** — it lives in `store/aiRun.ts`, above the view switch, and `components/AiRunHost.tsx` is mounted by `App` next to that switch. This is load-bearing, not tidiness: `AIView` is unmounted the moment another view is active, and while the run was component state, navigating away silently threw it away — the loop carried on (and carried on billing), but its answer landed on an unmounted component and was never saved, and a run parked on an approval could never be answered, so it held its progress forever. Anything a run owns (transcript, `busy`, streaming text, usage, the open chat's id, the id of the chat it is *running for*, parked transcripts, the approval) therefore goes in the store; what the *view* owns (composer, history/config panels, the Gerar Tasks review, attachments, the rename box) stays in `AIView`.

`AiRunHost` owns the two things that must not depend on `AIView` being on screen: the **conversation autosave** (an answer arriving while the user is on the Board still has to be written; its saves bump `savedTick`, which is how a mounted `AIView` knows to refresh its history list) and the **approval card**, rendered there and nowhere else so a background run can be answered instead of parking. Both bind Escape, and exactly one acts: the host binds it only when the AI view is closed, because `AIView` peels one layer at a time (a confirmation stacked on the card must take the press first) and a second listener would reach past that ordering.

`autoApprove` lives in the store too (a background run has to keep chaining actions), so `AIView` clears it **on entry when nothing is in flight** — otherwise "Aprovar tudo e continuar" on one run would hand the next one the same licence. Clearing it mid-run would park the very run it was turned on for.

**A run belongs to the chat that started it, not to the chat on screen.** `runningConvId` names that chat and **every append the loop makes goes through `routeRun` / `routeUsage`** — never to "the current transcript". Before this, switching chats mid-run swapped the target out from under the loop: the answer, its status lines *and* its token count landed in whichever chat the user had opened, and the autosave wrote them there. Two rules keep it honest:
- **`parked: Record<convId, {messages, usage}>`** holds a transcript the user has left mid-run. It can't be dropped (the answer is still coming) and can't be re-read from disk (the file is behind the run), so `openConversation` parks it on the way out and takes the live copy back — **ahead of the stored one** — on the way in. `AiRunHost` autosaves parked entries on the same terms as the open chat, or everything after the last save is stranded. Entries are only made when leaving a *running* chat.
- **`reset()` ("Nova") is not a wipe.** It spares a run in flight: no cancelling its approval (the card is the host's and shows wherever the user is) and no clearing `autoApprove`. It used to do both, back when a card raised by a chat you'd navigated away from was unanswerable. Tests that want a blank store must clear `busy`/`runningConvId`/`parked` **before** calling it, or a previous test's run leaks into the next one.

`busy` stays global — one run at a time, and it's what stops a second starting — but the transcript's live furniture (thinking bubble, "Parar", spinning status lines) keys off `runningHere` (`busy && runningConvId === conversationId`), or a chat would offer to stop work happening in another one. A run whose chat is **deleted** mid-run is aborted by `dropConversation`: there's nowhere to write, and every further step is billed and discarded.

**Chat titles are derived until they aren't.** The autosave derives one from the first user message on *every* save and knows nothing about renames, so a rename would be gone within the second. The rule therefore lives in **main**, not the renderer: `ai:conversations:rename` sets `titleCustom`, and `ai:conversations:save` ignores the caller's title once it's set. `replace` (backup import) must carry `titleCustom` through or a restore quietly un-names every renamed chat on the next save. Renaming deliberately leaves `updatedAt` alone — it orders the history by when a chat was last *talked to*.

`AIView`'s mount is still "entering the AI view": it reopens `AIConfig.lastConversationId` and lands on the last message. Two things keep that honest — `rememberConversation()` is driven by an effect on the store's `conversationId`, which covers every way the open chat changes (history pick, "Nova", and the first message of a new chat, whose id `send()` now mints up front so a run always knows where to land). The one case the effect **cannot** see is a `lastConversationId` whose conversation is gone: nothing changes there (the open chat was already none), so `handleLoadConversation` forgets it explicitly or the dead id is retried on every entry. `jumpToEnd` forces one scroll-to-bottom because a freshly loaded transcript sits at `scrollTop: 0`, which the normal "follow only if already at the bottom" rule reads as *not* at the bottom. The flag is consumed on use; latching it on would pin the view and stop the user reading back. The scroll effect is a `useLayoutEffect` so a restored chat paints at the end instead of flashing its first message.

`board`, `canvas`, and `files` share the project-scoped layout, so they are selected by a nested branch in `App.tsx` rather than the top-level one.

### AI assistant

`ai/` holds a tool-calling assistant that talks to any OpenAI-compatible provider (base URL + key + model, configured in the UI and stored in `ai-config.json`).

- `ai/tools.ts` — a single `REGISTRY` object is the source of truth: each entry pairs an OpenAI-format `definition` (sent to the model) with a `run` handler executed against the Zustand store. `TOOL_DEFS` and the dispatcher are derived from it, so **adding a tool means adding one entry** and nothing else. Tools are in Portuguese (`ler_tasks`, `criar_tasks`, `ler_financeiro`, …).
- Tools marked `write: true` mutate state (`criar_projeto`, `criar_tasks`, `atualizar_task`, `mover_task`, `concluir_task`, `deletar_task`, `iniciar_cronometro`, `criar_sprints`, `atribuir_sprint`, `criar_meta`, `atualizar_meta`, `marcar_habito`, `criar_transacao`, `criar_nota`, `rodar_agente_codigo`). `isWriteTool()` gates them behind user approval — `AiRunHost` asks (from whatever view the user is on) before running them unless automatic mode is on. **Keep `write: true` on any new mutating tool**; it is the only thing standing between the model and the user's data.
- **A tool result is not paid for once.** `msgs` accumulates all run and **every step resends all of it**, so what a read tool returns is billed again on each later step. Measured on real data: a bare `ler_tasks` on a 155-task board is ~8.5k tokens, ≈334k across a 40-step automatic run (the current default) — ≈125k at 15. Two things hold this down, and the first matters far more than the second:
  - `ler_tasks` takes **filters** (`busca` — title, accent- and case-insensitive; `tag`; `coluna`) and a **`limit`** (default `DEFAULT_TASK_LIMIT` 200, hard ceiling 500, nonsense falls back). Measured: the same board answers a targeted question in ~143 tokens instead of 8,553. It always reports **`total`** (how many matched) and **`truncado`** — without them a slice reads as the whole board and the model confidently answers the wrong count.
    - ⚠️ **`estado` defaults to `'abertas'`, so finished tasks are left out unless asked for.** Measured on the real DB, 185 of 413 tasks (45%) were already done — history that every later step of a run pays for again. `'concluidas'` and `'todas'` are the other two values; the retired boolean `concluida` is still **translated, never rejected** (an old transcript or cached schema keeps sending it, and erroring there burns a paid step to say "wrong argument"), and anything unrecognised falls back to the default rather than failing. `resolveTaskState()` owns all of that.
    - ⚠️ **The scope is one project** — `args.projectId`, or the active one; there is no cross-project search. So `total: 0` means "not in *this* project", and when the subject matched nothing while other projects exist the reply carries **`outros_projetos`** (id + name, capped at `OTHER_PROJECTS_MAX` 20) so the model retries there instead of answering "essa task não existe" about a task that does. Only on an empty subject — on a hit the sibling list is noise resent every later step — and **not** when `concluidas_ocultas` already explains the zero, or the model goes hunting through other projects for something it already found.
    - ⚠️ **The saving is only safe because the reply admits what it hid**: `concluidas_ocultas` counts what the state filter dropped, so `total + concluidas_ocultas` is the real board size, and `estado` is echoed back. Without those the default view is a silent lie — the model answers "you have 228 tasks" when there are 413, which is worse than the bill it saves. The count is taken against the *other* filters' matches, not the whole project, or a search would report unrelated finished tasks. Pinned by tests. The default cap sits above any real board today, so a bare call is unchanged; it's a ceiling against growth. Whether any of this helps depends on the **model choosing to filter**, which is why the system prompt says to.
  - `pruneSupersededResults()` in `agent.ts` blanks a tool result that a **later identical call** (same tool *and* same arguments) has replaced. Deliberately narrow: the message itself stays (the API demands one `tool` message per `tool_call` id — removing it is a 400), only read tools qualify (a write's result is an event, not an answer, so two identical `criar_tasks` are two things that happened), and the newest result for any question is always kept. It does **not** touch a single large result resent across many steps — nothing can safely, since the model may still need it. That case is fixed at the source, by filtering.
- ⚠️ **RAG/embeddings was considered here and rejected on measurement** — see the ticket trail. The corpus is too small to earn it: 395 tasks with ~45-char titles, and **all 19 notes together are ~159 tokens**, so indexing notes costs more than sending every one of them forever. There is also no `ler_notas` tool at all — the model can create notes but has never been able to read them. Revisit if the task count grows ~10x or notes stop being one-liners.
- `criar_projeto` wraps `store.createProject` (default columns seeded, colour validated against `PROJECT_COLORS`). Two things it must keep doing: **trim the name** (`createProject` stores it raw) and **refuse a duplicate name**, returning the existing `projectId` instead. `createProject` sets `activeProjectId` to the new project, so a twin would also capture the tasks the model creates next — the tool reports `ativo: true` and the approval card says so.
- `atualizar_task` edits an existing task's `priority` / `description` / `dueDate` / `tags`. It only touches the keys present in the args (`updateTask` spreads over the task, so an `undefined` value **clears** the field rather than skipping it), takes `""`/`[]` as an explicit clear, and **replaces** the tag list instead of merging. It validates `dueDate` as a real `YYYY-MM-DD` date and `priority` against `PRIORITY_CONFIG` — both are persisted, and a bad `dueDate` renders as "Invalid Date" for good.
- `mover_task` moves a task to another column by name, appending it to the end. It resolves the column **on the task's own project, never `args.projectId`** — `store.moveTask` looks columns up under `task.projectId`, so a column from another project would leave the task pointing at an id its board can't render. Crossing the Done boundary either way is a side effect of `store.moveTask` (completes on entry, reopens on exit, stops a running timer), so the tool reports `concluida`/`reaberta` back to the model.
- `criar_nota` creates one canvas note per call. `store.createNote` defaults every note to **(100,100)**, so `freeNoteSpot()` walks a grid over the project's existing notes and takes the first free cell — otherwise notes made from chat pile up and read as a single note. Placement is scoped to the target project, and sequential calls each see the previous note, so a run of them tiles. `NOTE_W`/`NOTE_H` mirror `createNote`'s default size; keep them in step.
- `criar_transacao` is the only tool that writes money. It stores `amount` as a **canonical decimal string** rounded with `toDecimalPlaces(2)`, matching `AddTransactionRow` so both writers agree. Three guards to keep: the amount must be **positive** (the sign lives in `type` — `ler_financeiro` sums expenses as positives); `parseMoney` **rejects thousands separators** instead of parsing them (`new Decimal('1.500')` is `1.5`, so guessing turns R$ 1.500 into R$ 1,50); and it **never picks between several tables** — a transaction in the wrong table is wrong twice over.
  - ⚠️ Its default date is the **local** day (`todayISO()` from `utils/habits.ts`), while `AddTransactionRow` defaults to the **UTC** day (the same-named `todayISO()` in `financial/shared.ts`). The two disagree after 21:00 in Brazil, which can file a transaction in the wrong month. The tool takes the local one deliberately; the shared.ts helper is untouched pre-existing behaviour.
- `marcar_habito` marks a habit done **today only**. `store.toggleHabit` *flips* the day, so the tool checks `completions` first and no-ops when already marked — calling it twice must never unmark. It has no "unmark" or "other day" mode. The day string comes from `todayISO()` in `utils/habits.ts`, built from **local** date parts to match HabitView's checkbox; `toISOString()` would tick tomorrow's box after 21:00 in Brazil. `vitest.config.ts` pins `TZ=America/Sao_Paulo` so local-date bugs can't hide behind a UTC test run.
- `criar_meta` / `atualizar_meta` wrap `store.createGoal` / `store.updateGoal`. Both validate `target` as a finite number **> 0** (`ler_metas` and `GoalView` divide by it) and reject a `projectId` that doesn't resolve. Neither touches `Goal.entries`: **a goal's progress is derived from its entries, so the AI can create and re-scope goals but cannot record progress** — `store.addGoalEntry` has no tool. `atualizar_meta` errors on an ambiguous title like `deletar_task`, and `ler_metas` returns each goal's `id` so the model can disambiguate.
- `deletar_task` is the only tool whose effect can't be undone (`store.deleteTask` — hard delete + tombstone, so a backup import won't bring the task back). It deletes one task per call and **errors on an ambiguous title** rather than picking a match, since deduplicating is exactly when titles collide. Note it runs unprompted under automatic mode, like every other write tool.
- `ai/system-prompt.md` — the assistant's system prompt, imported by `agent.ts` via `?raw` (Vite inlines it at build time, so there's no runtime file read and it works from a packaged asar; editing it hot-reloads in dev). **Everything in that file is sent to the model verbatim** — it's prompt text, so no comments or front-matter. Its wording is deliberately not pinned by a test: that would just move the string literal into the test file. It also carries the **"ask for only the data you need"** rule — the model is what decides whether `ler_tasks` is filtered or not, so that instruction is load-bearing for cost, not style. It now includes an **"Economize tokens"** section: an approximate per-operation cost table and a worked good-vs-bad example (`ler_arquivo` whole file ~60k tokens vs `buscar_no_codigo` + scoped read ~3.5k), the anti-redundancy rule (don't re-search a variation you already covered), and the "jump to the line the search returned" rule (`simbolo`/`linha_inicio`). These are load-bearing for cost because the model is what chooses to filter and scope — but since only the model reads them, none of it is pinned by a test. ⚠️ Still worth a pass: the read-only framing is gone, but the prompt gives no guidance on the write tools it can now call.
- `ai/agent.ts` — the loop. `runAgent` iterates model→tools→model, capped so a misbehaving model can't spin forever. Every call goes through the main process rather than the renderer.
  - **Tool calls are announced as they're composed.** `ai:chat:delta` carries two kinds of payload: `{delta}` for text and `{tool: {index, name}}` when a tool call's name arrives. The gap it closes: a step that calls a tool with **no preamble streams no text at all**, so `onStream` never fires and the only thing on screen was an anonymous spinner for as long as the arguments took — seconds, for a `criar_tasks` carrying twenty. The name lands in the first delta; only the arguments are slow. Three rules: each field is **checked before use** (a tool payload has no `delta`, and passing it through appends the string "undefined" to the answer); the name is **re-sent if it arrives in pieces**, keyed by index, so a partial corrects itself instead of duplicating; and `runAgent`'s `onToolStream` fires with `[]` both when the message completes (the persistent `onStatus(_, 'tool')` lines take over — both on screen would read as two tools running) and at the **start of every retry attempt**, exactly like the stream buffer. `AiRunState.streamingTools` is transient and never reaches disk.
  - ⚠️ **`describeToolActivity(name, args)` must survive empty `args`** — it labels a call being *composed* as well as one running, so a case that interpolates a missing arg states a falsehood. `Criando 0 task(s)` was shown while the model wrote a call creating twenty, and `criar_transacao` defaulted to `despesa` before the model had said which way the money went. Every case degrades to the generic verb. A test asserts **every** tool in `TOOL_DEFS` has a label, so a new one can't surface as a raw identifier mid-chat.
  - **Token usage / cost.** `ai:chat` and `ai:chat:stream` forward the provider's `usage` (normalised to `{promptTokens, completionTokens}`); `runAgent` reports it per call via `onUsage`, and `AIView` sums it — **every call is billed, so the total is the sum over all tool rounds**, not the last prompt's size. It persists on the conversation (`ai-conversations.json`), and absent usage means *unknown*, not zero: the header hides the counter rather than claiming a conversation was free. Streaming only reports usage if asked (`stream_options: {include_usage: true}`), and a strict provider answers 400 to that, so the stream falls back to a plain request — losing the count, never the answer. At the end of a run `runAgent` also logs a **cost breakdown** to the console (`summarizeRunCost`, pure/tested): total tokens, an optional USD estimate (only when both prices are set), and the three costliest calls labelled by the tools their step ran — a production diagnostic for spotting waste. ⚠️ The per-call figure is the whole accumulated prompt, **not** one tool's share; the label names what the step did so a costly step is recognisable, but the tokens can't be attributed to a single tool. Silent when the provider billed nothing. The same per-step figure also rides on `StepProgress.tokens` (filled in after the call, before the step's status lines fire, and carried through `aiRun`'s status message to `AIView`'s `StatusLine`), so each line in the chat trace shows a `… tok` badge next to its `N/40` — what that step cost, growing each step as the history is resent. Absent when the provider reported no usage (unknown, not zero); the several tool lines of one step share the same figure, since one model call produced them all.
  - **Spend log.** Every billed call is appended to `ai-usage-log.json` by the **main process** — the choke point every model call passes through, so no caller can forget to report. `main/usage.ts` holds the rules (no Electron import, hence the only main-process code with tests: `src/main/__tests__/usage.test.ts`); `main/index.ts` does the file IO and exposes `ai:usage:summary` (today / last 30 days / total / by model / last 30 calls), which the chat header's token chip opens. Two invariants: each entry's **cost is frozen at the prices configured when the call ran** (re-pricing history against today's numbers would rewrite what past calls cost), and buckets **count `unpricedCalls` separately** rather than summing them as zero — a total that hides them reads as the full story when it isn't. The log is capped at `MAX_USAGE_ENTRIES`.
  - **Run metrics.** A sibling of the spend log, one record **per run** instead of per call: `main/run-metrics.ts` holds the rules (no Electron, tested in `src/main/__tests__/run-metrics.test.ts`), `main/index.ts` does the IO (`ai-run-metrics.json`) and exposes `ai:run-metrics:append` / `ai:run-metrics:summary`. Where it differs from usage: the renderer's `runAgent` is the **only** place that can count a run's `steps`, `redundantSearches` (fuzzy-dup search warnings) and `repeatedReads` (read brakes that fired), so the renderer computes the metric in its `finally` and **sends** it up — best-effort, fire-and-forget, guarded so an absent bridge (older preload, tests) is a no-op and a failed write never touches the run. `summarizeRunMetrics` rolls it up **per model with per-run averages** (`avgTokensPerStep` is the fair cross-model number, since runs vary in length), so "does Flash burn more than Pro for the same task?" becomes visible over time. Recorded only once a round completed (`stepsRun > 0`), so an instant-abort logs nothing. ⚠️ A provider that reports no usage logs a 0-token run — it buckets under that model's name, and the token averages read low for it; the steps/waste signals stay meaningful.
  - **Cost is never invented.** `AIConfig.inputPricePer1M` / `outputPricePer1M` are user-set USD prices; there is deliberately no built-in price table, because the same app talks to OpenAI and to a free local model. Both must be set or no cost is shown — pricing with one would charge half the tokens at zero. It's a display estimate, so plain floats are fine here (unlike the financial module's decimal strings).
  - **Two-model routing.** `AIConfig.modelComplex` is an optional heavier model; when set, `routeModel(lastUserText, cfg)` picks it for a run whose triggering message reads like a code/analysis task (`COMPLEX_TASK_PATTERN` — accent-stripped ASCII stems: `codigo`, `bug`, `refator`, `arquitetura`, `investig`, …) and leaves the cheaper `model` for everything else. **Absent = one model for everything**, the previous behaviour, so runs without it configured are unchanged (and `routeModel` returns `cfg.model` verbatim). The choice is made **once per run** in `runAgent` — `const rcfg = { ...cfg, model: routeModel(...) }`, and *every* call the loop makes uses `rcfg`, so a run never switches model mid-flight; a follow-up question is re-classified on its own words. The keyword set is kept deliberately close to the user's list — over-matching sends cheap questions to the pricey model and raises the bill this exists to lower. Configured in the AI view (a "Modelo p/ código" select, empty = same as principal) and persisted like the rest of the config. The spend log's per-model breakdown makes the split visible after the fact.
  - Model calls go through `callModelResilient`, which retries a failed call up to `MAX_RETRIES` (3) with exponential backoff + jitter. A run holds all its progress in `msgs`, so one 503 on the last step used to throw the whole thing away. Three rules: **only the model call is retried, never tools** (a replayed `criar_tasks` would duplicate data); **`isRetryable(status)` gates it** — 408/429/5xx and no-status (transport) retry, while 4xx like 401 fail fast because retrying a bad key only delays the real message; and **the stream buffer resets per attempt**, or a half-streamed dead attempt gets prepended to the retry's text. `ai:chat` / `ai:chat:stream` forward the provider's HTTP `status` for this (`errorStatus()` in `main/index.ts`); the pre-flight config check reports `400` so it isn't retried. Retries announce themselves via `onStatus`, since a silent multi-second stall reads as a hang.
  - The cap comes from `resolveMaxSteps(config.maxSteps, autoApprove)`. **The step cap and the approval mode are deliberately separate**: an explicit `maxSteps` wins in *both* modes, so you can raise the ceiling while still approving each write (previously the only way past the manual default was automatic mode, which also surrenders approval). Unset → `MAX_STEPS` (40) manual, `AUTO_MAX_STEPS` (100) automatic. ⚠️ **Both are deliberate settings, and 100 is the expensive one**: every step resends the whole accumulated history, so the last steps of a long run cost far more than the first and the total grows worse than linearly in the cap. The pair has moved twice on request (15/40 originally, briefly 15/15 as a cost measure, now 40/100) — someone who wants a shorter run sets `maxSteps` explicitly, and turning automatic mode on quotes what a full run is likely to cost (`estimateAutoRun`, priced off the user's own logged calls, and silent when there is no sample to price from). Anything invalid (0, negative, NaN, a string hand-edited into `ai-config.json`) falls back to the default; everything is clamped to `MAX_STEPS_LIMIT` (100), including inside `runAgent`, because each step is a paid model call. **`MAX_STEPS_LIMIT` must stay ≥ `AUTO_MAX_STEPS`** — it is the clamp, so a lower limit would silently cap automatic runs below their own documented default. `AIConfig.maxSteps` is optional and persists in `ai-config.json` — the loader must keep passing it through, or the setting silently reverts to the default on every boot.
  - **A soft brake catches a model looping on the same read**, complementary to the step cap. `runAgent` counts each read call by signature (tool name + JSON args) in `readRepeats`; on the `READ_REPEAT_LIMIT`-th (3) identical call it **doesn't run the tool** and feeds back a synthetic result telling the model to answer with what it has. It's a *nudge, not an abort* — the result goes back as an ordinary `tool` message, so nothing is discarded and a model that takes the hint concludes on the next step instead of burning the rest of the budget re-fetching an answer it already has. **Reads only** (`!isWriteTool`), the same line `pruneSupersededResults` draws: two identical writes are two events, not a loop. The two are siblings — prune blanks the *cost* of a repeated read, the brake stops *running* it. Two more run-scoped nudges ride alongside it: a **blind whole-file re-read brake** (`BLIND_FILE_READ_LIMIT` 2) fires when `ler_arquivo` is called on the same path twice with no targeting arg (`simbolo`/`linha_inicio`/`linha_fim`/`inicio`) — tighter than the exact brake because a second read of a whole file is almost always a re-fetch, and paged/scoped reads are deliberately **not** counted; and a **fuzzy-search warning** appends an `aviso` to a `buscar_no_codigo` result whose term is a substring of an earlier one this run (`backup`→`exportBackup`). The warning *never blocks* — the search still runs — since a substring is a genuinely different query, not a loop; it only nudges the model to reuse what it already fetched. Both live in `runAgent` (run-scoped state), **not** `tools.ts`, whose handlers are module-global and shared across every conversation.
- The assistant can read a project's source when the project has code paths selected: `listar_arquivos`, `ler_arquivo`, `buscar_no_codigo` map to the `ai:code:*` handlers, which confine every path to the given root. A project can have **several roots selected at once**, so these tools take an optional `pastaId` to narrow to one and otherwise fan out across all of them (`activeRoots()` in `tools.ts` resolves the list). `ler_arquivo` errors instead of guessing when the same relative path exists under more than one root. It is **paged, not capped-and-dropped**: `ai:code:read` returns at most `CODE_READ_PAGE` (20000) chars — a whole file is resent on every later step, so a 60k-char file was a ~15k-token per-step tax for a question that usually needs a slice — reporting `total`, the slice's `offset`, and a `nextOffset` when `truncated`; the tool exposes `inicio`/`max_chars` so the model pages through the rest (`inicio = nextOffset`) instead of pulling it whole. `max_chars` can raise a single read to `CODE_READ_MAX` (60000), the old ceiling, so a genuinely large read is still possible on demand. ⚠️ A **blind read of a big file** (no scope, no `inicio`, no explicit `max_chars`, and `total > CODE_READ_PAGE`) no longer returns a full 20k window: it returns the first ~100 lines plus the `simbolos` map, a `nextOffset` to page on, and a `dica` steering the model to `simbolo`/line-range/`inicio`. An explicit `inicio` or `max_chars` bypasses it — the model already knows what it wants. The 5000-line threshold the request suggested was a no-op (the largest real file is ~1k lines), so the guard keys on the same char boundary the paging already uses. **`ler_arquivo` also reads by scope**: `simbolo` extracts one function/class/const (~1-3k chars via `extractSymbol`), `linha_inicio`/`linha_fim` a line range (`extractLines`) — the cheap path is `buscar_no_codigo` → take the `linha` → read just that scope, instead of paging the file whole. A `simbolo` that isn't found returns `simbolos` (the file's declaration map) so the model picks a real one rather than guessing. `listar_arquivos` is paged the same way and for the same reason — with several roots selected it fans out, so a flat 400-per-root cap put ~1200 paths in one result, resent every step: `ai:code:list` now walks up to `CODE_LIST_WALK` (2000) to report a real `total`, returns one `CODE_LIST_PAGE` (200) window with `offset`/`truncated`/`nextOffset`, and takes `inicio`/`max_arquivos` (ceiling `CODE_LIST_MAX` 400) to page or widen — or narrow the tree with `subpasta`. `buscar_no_codigo` stays capped-and-dropped (60 matches): a search hit is already a filtered answer, not a listing to walk. Its results are **grouped by file** in the tool layer (`{ arquivo, ocorrencias: [{linha, texto}] }`), so the path isn't repeated per hit and the model can feed a `linha` straight into `ler_arquivo`'s scoped read; the `ai:code:search` IPC shape stays flat (`matches`), so its handler and `handlers.test.ts` are untouched. `buscar_no_codigo` results are also **cached in the renderer** by `(sorted roots + normalised term)` for `CODE_SEARCH_TTL_MS` (30s), since a run often re-searches near-duplicate terms and each result is resent every later step; the cache is dropped whenever a code-agent run is fired (`clearCodeSearchCache()` in `rodar_agente_codigo`), which edits files. ⚠️ Within the TTL a file edited *outside* the app (an editor, git) can return a stale hit — the short window bounds staleness the renderer can't observe.
- `rodar_agente_codigo` runs the **native code agent** (`src/main/code-agent.ts`), a tool-calling loop that edits code with the app's own provider. ⚠️ **This replaced the external `codex` CLI.** The trade is deliberate and documented, not hidden: codex ran the model's edits inside an **OS-level sandbox** (Seatbelt/macOS, Landlock/Linux) and authenticated itself; the native agent has **neither**, so the only barriers between the model and the disk are (1) `confineToRoot` (every path pinned to the project folder) and (2) **per-action approval** asked before any write or command. Both are load-bearing.
  - **The loop lives in `code-agent.ts` and is pure/injectable** (`callModel`, the command runner and the approval prompt are all passed in), so the five tool handlers and the loop are tested against a temp dir + a stub provider in `code-agent.test.ts`. `index.ts` wires the real provider (`callCodeModel` via `getOpenAIClient`), the IPC approval round-trip and `child_process`. Five tools, in Portuguese: `listar_arquivos`, `ler_arquivo`, `buscar_no_codigo` (all read, run without asking), `escrever_arquivo`, `executar_comando` (both `needsApproval` → gated). The loop caps at `CODE_AGENT_MAX_STEPS` (30) and forces a final text answer when the cap bites.
  - **Per-action approval is an IPC round-trip.** When the loop hits a write/command it sends `ai:code-agent:approve-request` (`{id,name,args,resumo}`) and parks on a promise held in `pendingApprovals`; the renderer shows the card and answers via `ai:code-agent:approve-response`, which resolves it. `stopCodeAgent()` sets the abort flag **and** denies every parked approval — a loop waiting on a card the user will never see again must not hang. There is no child process anymore: "stop" is an abort flag checked between steps, not a `kill`.
  - **`executar_comando` uses async `exec`, not `execSync`** — `execSync` would freeze Electron's main event loop (and its IPC/window controls) for the command's whole duration. Timeout + output cap (`COMMAND_OUTPUT_CAP`) are enforced; a timeout is reported as `timeout: true`, not a plain non-zero exit.
  - **`src/main/ai-jail.ts` — the mandatory OS-level sandbox for those commands** (https://github.com/akitaonrails/ai-jail). Per-action approval covers *intent*; ai-jail covers *reach* — on Linux it wraps the command in bubblewrap (+Landlock/seccomp), on macOS in `sandbox-exec`, masking SSH keys / cloud creds / everything outside the project. **The sandbox is required by default** (`AIConfig.sandboxEnabled` absent = on; only an explicit `false` runs unconfined). The run handler **refuses to start** (`getJailStatus()` gate) when the sandbox is required but ai-jail isn't available — the user installs it (onboarding) or unticks the box. When active, the run's `CommandRunner` wraps each command via `wrapCommand` → `ai-jail --rw-map <projectDir> -- /bin/sh -c '<cmd>'` (⚠️ **there is no `--workdir` flag** — confinement is expressed as mounts; `--rw-map` is the writable project root), with `jail.path` the **absolute** binary path from detection (PATH may miss `~/.local/bin`, the codex problem again). A failure matching `looksLikeSandboxBlock` gets a `⛔ ai-jail bloqueou…` note (advisory only — a narrow regex, never a wrong result).
    - **Only the pure logic is unit-tested** (`ai-jail.test.ts`): `assetFor` (only `ai-jail-linux-x86_64.tar.gz` and `ai-jail-macos-aarch64.tar.gz` exist upstream — **no Windows `.exe`, no macOS-Intel binary**; pinned to `AI_JAIL_VERSION`), `wrapCommand`, `looksLikeSandboxBlock`, `parseSha256`/`parseVersion`, and `detectAiJail` with an injected `Exec`. The installer (download → **sha256-verify** → `tar -xzf` → `~/.local/bin` → chmod → `--version`) and brew path are IO, verified in-app.
    - ⚠️ **Windows runs the sandbox *through WSL2* — ai-jail has no native Windows build.** Detection on Windows skips the native PATH loop and instead looks **inside** the default WSL distro (`wsl -e bash -lc 'command -v ai-jail && ai-jail --version'`, a login shell so `~/.local/bin` is on PATH), keeping the WSL absolute path and setting `viaWsl: true`. When `viaWsl`, the run's `CommandRunner` uses `runSandboxedWsl` → `wsl -e <ai-jail-abs> --rw-map <wsl-project> -- bash -c 'cd <wsl-project> && <cmd>'` (**argv, never a shell string** — nothing has to survive cmd.exe→wsl→bash quoting), with `winToWslPath` mapping `C:\proj` → `/mnt/c/proj`. ⚠️ **Consequence:** on Windows the command runs in the **WSL Linux environment**, not native Windows — different tools/paths. Onboarding is a two-step flow: no WSL2 → show `wsl --install` (admin + reboot, **offered, never run silently**); WSL2 present but no ai-jail → show `WSL_AI_JAIL_INSTALL_COMMANDS` (apt bubblewrap + download the linux tarball into WSL's `~/.local/bin`; interactive sudo, so the user runs them). `installAiJail` still refuses on Windows (the app can't drive the interactive WSL install). Detection only runs when the sandbox is **on** — a disabled sandbox skips it, so a plain run never spawns `wsl`.
    - ⚠️ **Linux needs `bubblewrap`** (`bwrap`) present, and hardened kernels (Ubuntu 23.10+) restrict the namespaces it uses — the same gap documented for codex. `detectAiJail` reports `bubblewrap` so the UI can say why an installed ai-jail still won't confine.
  - **The system prompt is assembled per run** (`buildSystemPrompt`): behaviour rules (edit existing files over new ones, keep the surrounding style, don't commit), the repo's `GUIDE.md`/`AGENTS.md` if it has one (`readProjectGuide`), a compact file tree (`dirTree`), and the pinned files. Still a **single cwd**, so it can't span roots — with more than one selected the tool errors asking for `pastaId`. Still **fire-and-forget**: the run handler returns `{success:true}` at once and the loop runs async, streaming to the panel.
  - **The real model is surfaced** (was "modelo: próprio do codex"): the opening banner line names `modelo: <model> @ <baseUrl>`, `ai:code-agent:status` returns `model`, and the panel header shows it. Tool steps stream to the panel as `[tool] …` / `[resultado] …` log lines **and** as structured `ai:code-agent:tool` events. Model calls are billed through `appendUsage` like the chat.
  - ⚠️ **Removed codex remnants, kept dormant:** two pure helpers — `resolveExecutable` and `detectAgentHint` — remain in `index.ts` with their unit tests but are **no longer wired into anything**. They can be deleted in a follow-up. The old `buildAgentCommand`/`killCodeAgent`/sandbox-flags/`guideIn` path was removed. The archive's `AgentRunMeta.agent` field is now **free text** holding the model name (old rows without it read back as `"codex"`).
  - 📎 **HISTORICAL — the codex sub-bullets below (PATH resolution, headless stdin, `--sandbox`/bypass flags, the bubblewrap hint, the `codex exec` prompt/stdin plumbing) describe the REMOVED external path.** They are retained as background, not as current behaviour. What they say about the **diff, the log buffer, the run archive and the run picker (`code-diff.ts`, `agent-runs.ts`, `AgentTerminal`/`AgentRunPicker`, `captureBase`/`diffSince`/`archiveAgentRun`) is still accurate** — that machinery is reused unchanged by the native agent, only the base is captured before the loop (not the spawn) and the diff still spans base→working-tree. When editing the code-agent, trust `code-agent.ts` + the native-agent bullets above over anything below that mentions `spawn`/`codex exec`.
  - ⚠️ **"On PATH" is not the same PATH the user sees, and `resolveExecutable` exists for that gap.** A GUI-launched Electron app does not inherit the shell's PATH: measured on Ubuntu 24.04 + GNOME/Wayland, an app started from the launcher gets the **systemd user manager's** PATH, while `npm config set prefix ~/.npm-global` puts codex in a dir added only by `~/.bashrc` — read by interactive shells and nothing else. Symptom: `codex --version` works in a terminal and the panel says `"codex" não encontrado`, which is a lie about the cause and sends the user off reinstalling something already installed. So the lookup **searches PATH first, then `fallbackBinDirs()`** (`$NVM_BIN`, `~/.npm-global/bin`, `~/.local/bin`, volta/bun, plus homebrew on darwin) and hands `spawn` the **absolute path** — passing the bare name back would just re-do the lookup that already failed. POSIX matches are checked for the **executable bit**, or a same-named non-executable file defers the failure to spawn as `EACCES`, a different problem than the one it is. Deliberately not `npm prefix -g`: authoritative, but it costs a subprocess per run and needs npm on PATH — the very thing missing in the case this fixes. Note the app can only fix *its own* lookup; a user wanting the dir everywhere sets it in `~/.config/environment.d/` (systemd reads it for the graphical session — `~/.profile` is **not** reliably read under Wayland).
    - ⚠️ **The fallback re-opens the "real codex spawns in tests" trap, and `SAGYOU_DISABLE_BIN_FALLBACK` is what closes it.** The not-installed test proved its path by emptying PATH — which no longer suffices, because the fallback dirs are *exactly* where a dev machine's codex lives (`~/.npm-global/bin` on Linux, `/usr/local/bin` on a Mac). The env var drops every fallback dir and is set by that test alone. Keep it honest: a test asserts `fallbackBinDirs()` is non-empty **without** it, so the opt-out can't silently disable the feature in the app.
  - **Spawned headless, so it must be told it is.** stdin is a pipe **only** to deliver the prompt (see below) and is ended immediately; it is never a terminal. A closed stdin turns any stray confirmation into an immediate EOF instead of a process that hangs "running" forever.
  - **The agent must never commit.** Writing to someone's git history is not ours to do: the diff panel exists so the **user** reviews and commits. `codex exec` already leaves the tree dirty, which is the wanted shape — `captureBase` runs before the spawn and the diff spans base→worktree, so nothing is lost by not committing. Pinned by a test.
  - **The child's output is decoded as UTF-8 explicitly**: `child.stdout/stderr.setEncoding('utf8')` rather than a per-chunk `d.toString()`, so a multi-byte char whose bytes straddle two `data` events is buffered and joined instead of splitting into a replacement glyph — the Portuguese accents in the panel (`não` → `nÃ£o`) were this.
  - **The panel renders the log as a terminal, not a `<pre>` (`components/AgentTerminal.tsx` + `utils/ansi.ts`).** The log is a *pipe*, so whatever ANSI the agent emits arrives as literal bytes — `parseAnsi` turns SGR colour/intensity into styled segments, **strips** the cursor/OSC codes a `<div>` would otherwise show as garbage, and **applies** `\r` and erase-in-line (`\x1b[K`, all three variants) so a redrawing spinner doesn't stack. ⚠️ **The overwrite is resolved line-by-line as the parser runs, never as a pre-pass over the raw string** — that was the old shape and it can't work, because the escape bytes are still in the way: a redraw re-emitting its colour (`\r\x1b[32mok`) had the escape counted as text, and an `\x1b[2K` clear was dropped rather than applied, leaving the erased text on screen under its replacement. A redraw also must not erase the *finished* lines above it. All three are pinned by tests. Deliberately partial (SGR only; 256/truecolour and backgrounds are swallowed, never leaked as text) and **pure/tested** (`utils/ansi.test.ts`) — the component itself (autoscroll-follows-tail, terminal chrome) isn't.
  - **Pinned target files (`request.files`) focus the run.** codex has no `--file`, so they are **named in its prompt** instead — it navigates the tree with its own grep/read tools, and saying which files to edit spares it that search. The tool takes `arquivos` (relative paths); the model is told to locate them with `buscar_no_codigo` first and pass them. Main **confines each to the root** (`confineToRoot`, same barrier as the read tools — the path is the model's) and drops any that escape or don't exist, so a bad list silently falls back to discovery and can only speed things up.
    - ⚠️ **"Silently" was the problem, so the run now opens with a banner** naming which path it took: how many files were pinned (and which), or that none were and the agent is about to discover them, plus any **dropped** paths and the fact that they are why it fell back. The two paths were **indistinguishable from the panel** — a path the model got slightly wrong is dropped in silence and degrades to discovery, and `arquivos` is optional so "did the model even send it?" was unanswerable after the fact. The banner also **names the model**, and what it says is that codex uses **its own login and its own backend** (it gets no `--model`; the `OPENAI_*` env doesn't redirect it) — so the app's configured provider has no bearing on a code run, and nobody reading the panel should think it does. Emitted through `emit`, so it is in `codeAgentLog` and survives an unmounted panel like everything else. Pinned by tests in `handlers.test.ts`.
    - **The run closes with `[sagyou] duração: N.Ns`.** The panel had no clock at all — the exit line carries a status code and nothing else — so "how long did that take?" could only be answered with a stopwatch. Also via `emit` (not `appendAgentLog`) so it both streams and buffers: the exit line itself can't carry the duration, because the renderer writes its own copy of that line on the `ai:code-agent:exit` event. The clock starts as late as possible, immediately before `spawn`, so it times the agent and not our own banner or the `captureBase` before it. What codex *does* need is write permission, and how it gets it is **platform-split** (`sandboxArgs` in `buildAgentCommand`). `codex exec` is already non-interactive (it never prompts for approval), so there is **no** `--ask-for-approval` — that flag is top-level only and `exec` rejects it with exit code 2; `exec` exposes no `--full-auto` either, only `-s` and the bypass below. On **Unix**, `--sandbox workspace-write`: codex's sandbox is OS-level (Seatbelt on macOS, Landlock on Linux), so it genuinely confines writes to the workspace while letting it edit — read-only would let it plan edits it can never apply, `danger-full-access` is wider than needed. On **Windows**, `--dangerously-bypass-approvals-and-sandbox`: there is **no sandbox backend**, so `--sandbox workspace-write` is silently downgraded to read-only and codex reads the code, reports success, and **writes nothing** (verified in the wild and reproduced — the symptom that motivated this). The bypass is the *only* way `exec` can write on Windows; it is not "safe vs unsafe" (Windows gives no OS confinement either way) but "writes vs can't write", and `rodar_agente_codigo` is already gated behind explicit user approval before the spawn. ⚠️ **Keep this a `process.platform === 'win32'` branch** — using the bypass on Unix would throw away the real sandbox that platform can enforce.
    - ⚠️ **On Linux, `workspace-write` can fail outright, and it fails quietly with exit 0.** codex's Linux sandbox goes through **bubblewrap**, which needs unprivileged user namespaces; **Ubuntu 23.10+ restricts those by AppArmor** (`kernel.apparmor_restrict_unprivileged_userns = 1`, the default on 24.04). codex then can't run *any* command — observed as `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted` — so it reads nothing, writes nothing, reports the obstacle in prose and **exits 0**. This is the Linux sibling of the Windows failure above: from the app's side a run that changed nothing looks like a run that decided nothing was needed. The diff panel is what tells them apart; the exit code does not. Not worked around in code (loosening the user's kernel hardening is not ours to do) — the fixes are `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, an AppArmor profile for the codex binary, or `--sandbox danger-full-access` accepting there is then no confinement.
      - **It is detected and explained instead** (`detectAgentHint`, pure and tested): the child's output is watched through a rolling 4000-char window — its own, *not* `codeAgentLog`, which is capped to the panel's tail, and this warning is the **first** thing codex prints, so on a chatty run it would scroll out before anyone looked. A window rather than a per-chunk test because a marker can straddle two `data` events. The result goes to the renderer through **`ai:code-agent:status` (`hint`), not the exit event** — the event carries only a status code, and this failure's code is `0`. `AIView` renders it as a card **above the diff** (it explains why the diff is empty) and it is also written into the log, so a pasted transcript carries the diagnosis with the symptom. Cleared per run, on the same terms as the log: a diagnosis held over from the previous run would blame a healthy one. ⚠️ **The card offers the command to copy, never to run** — it needs sudo and it weakens the user's kernel hardening, so the app must not make that call for them; likewise it does not silently downgrade the sandbox behind the user's back.
    - **Pinned files are named to codex relatively** (`relative(dir, f)`): `files` arrives absolute from `confineToRoot`, so joining it raw made the prompt say "caminhos relativos à raiz" and then give an absolute path — self-contradictory, and it put the machine's home directory in the model's context for nothing (the same leak the guide path is careful to avoid). codex runs with `cwd = dir`, so relative is also the form it can use. Pinned by a test. **The prompt reaches codex over stdin (`codex exec … -`), never as an argv token.** On Windows codex is a `.cmd`, so it runs through `cmd.exe` (`shell: true`), which word-splits a bare multi-word prompt into separate args (`Antes de …` → codex fails with `unexpected argument 'de'`). So `buildAgentCommand` returns `stdinData`, the handler opens stdin as a pipe only when it's set, writes the prompt and ends it; the `child.stdin` `error` handler swallows the EPIPE a failed spawn would raise.
  - **Main buffers the agent's output (`codeAgentLog`), because the panel outlives nothing.** The child process runs for minutes and the user is meant to keep working; `ai:code-agent:output` is a live stream, and the only thing accumulating it was `agentLog` inside `AIView`, which unmounts the moment another view is active. Everything printed while the user was elsewhere reached a listener that no longer existed, and an agent that *finished* while they were away left nothing at all. Verified in the real app: leave mid-review and the tail of the review is gone for good. `ai:code-agent:status` now returns `{running, log}` and `AIView` reads it **on mount** (replacing, not appending — appending would double every line for a user who never left). The main-side cap equals the panel's own (`MAX_AGENT_LOG` 8000) **on purpose**: leaving and coming back must show exactly what staying would have. The buffer resets per run, but only once a request is known good — a refused start must not wipe output the user is still reading.
  - **The diff (`code-diff.ts` + `components/CodeDiff.tsx`, `ai:code-agent:diff`).** ⚠️ **The base is captured *before* the agent spawns** (`captureBase` in the run handler) and that ordering is the whole feature: `git diff` after the fact cannot tell the agent's work from what the user already had in progress, and showing someone's own half-finished edits as *"what the AI did to your code"* is worse than showing no diff at all.
    - `git stash create` is what makes it work: it writes a commit object for the current working tree and **touches nothing else** — not the tree, not the index, not the stash list — so it is safe against a repo with live work in it (pinned by a test). It prints nothing on a clean tree, where HEAD already describes it. `null` (no repo, or no commits yet) is a legitimate state meaning "no diff", and must never block the run.
    - `codex exec` leaves the tree dirty, and a diff from a base commit to the working tree spans commits and uncommitted edits alike. **Untracked files are the exception** — `git diff` cannot see them, so each is fetched with `git diff --no-index` (`git add -N` would do it in one call and leave the user's index modified behind their back).
    - Computed **on demand**, not captured on exit: it is derived state, so a panel that was unmounted when the agent finished can still ask, and re-reading is free.
    - Never through a shell: `dir` is a user-picked path and the args carry filenames, so a file named `; rm -rf ~` would become someone else's command. `execFile` with an args array.
    - The renderer's `parseDiff` lives in `utils/diff.ts`, not beside the component (fast refresh needs component-only exports). Two traps it exists to avoid: the `+++`/`---` headers are **dropped** (a naive parser renders every file as one addition and one deletion of its own name), and only the *terminating* newline is trimmed before splitting — blank lines inside a hunk are real structure.
    - "Changed nothing" and "no diff available" are **opposite facts**, rendered differently: an agent that only read the code is a common outcome, while "not a git repo" said as "nenhum arquivo alterado" is a lie about the user's code. **A third fact joins them once the diff is shown mid-run**: an empty diff while the agent is still working means "not yet", not "never", so `CodeDiff` takes `running` and says so — otherwise the panel announces "changed nothing" about a run that hasn't finished reading.
    - **The panel leads with the diff, not the log.** "Mudanças" renders *while* the agent runs (polled every 2s; derived in main from a pre-spawn base, so re-asking is cheap and idempotent — codex leaves the tree dirty, so the diff shows the work mid-run), and `AgentTerminal` moved behind a "Log completo" toggle. The reasoning: "what is it doing to my code" is answered by the changed files, and a redrawing status line answers it badly — it shows one step at a time and keeps no history. The log stays one click away as the debugging view (why it failed, what it read). The interval is not the only refresh — the `code-agent:exit` handler still calls `loadDiff()` once, so the final state lands even though the interval clears the moment `agentRunning` goes false.
  - **Past runs are reopenable, and they are frozen snapshots (`agent-runs.ts`, `components/AgentRunPicker.tsx`, `ai:code-agent:runs` / `:run-get`).** The panel's header carries a picker listing the runs of the open chat; selecting one swaps **both** the log and the diff for that run's archive. ⚠️ **The diff is written once, when the agent exits, and is never re-derived.** Re-running `diffSince` later would measure a base against *today's* tree and present every edit the user has made since as the agent's work — the same lie `code-diff.ts` exists to prevent, just displaced in time. Storing the base commit instead of the text would be smaller and would reintroduce exactly that bug. The UI states the distinction rather than hiding it: a snapshot is labelled "snapshot de quando a run terminou", `CodeDiff`'s `onRefresh` is **omitted** (so there is no button offering to recompute), and `running` is forced false — the spinner and "Parar" belong to the live run only.
    - **The payload is files under `userData/agent-runs/`, not fields on the conversation** — `ai-conversations.json` is re-read and rewritten whole on every autosave *and* every keystroke of the history search, so a log (8k) plus a diff (up to 200k) inlined there is the base64-screenshot mistake again. So: `<id>.json` per run for the heavy part, and a small `index.json` of metadata the picker lists without touching any of it. `isRunId()` is the **security guard** (the id comes back from the renderer, so it is a path in disguise), the twin of `isImageFileName`.
    - `pruneRuns` caps **per conversation first** (`MAX_RUNS_PER_CONV` 20), then globally (`MAX_RUNS_TOTAL` 100): a purely global cap would let one chatty project evict every other chat's history. It returns the dropped rows and the caller **unlinks their payloads** — an index that forgets a run without deleting its file leaks that disk for good. Pinned by a test asserting every run lands in exactly one of `keep`/`drop`.
    - **`ai:code-agent:archived` is a separate event from `:exit`, on purpose.** Archiving costs a `git diff`, and the panel must not stay on "rodando" waiting for it — so exit flips the UI immediately and `archived` tells the picker its new row exists. The alternative (refreshing on `exit` after a guessed `setTimeout`) races the write for an index it hasn't finished rewriting.
    - The run is tagged with **`runningConvId`, not `conversationId`** (`rodar_agente_codigo` in `tools.ts`): a run belongs to the chat that started it, not to whichever one the user is looking at when it finishes — the same rule `routeRun` follows. Without the tag a run is archived under no conversation and the picker, which lists by convId, can never show it. Pinned by a test.
    - `codeAgentRun` (main) holds the in-flight run's identity and is **nulled by `archiveAgentRun`**, which is why a run can't be archived twice: both exit paths (`'error'` and `'close'`) can fire for one run. Archiving is best-effort throughout — it must never break the run, which already did the work the user asked for.
    - The panel now also renders when the chat has runs to reopen but no live output (`agentLog || pastRuns.length > 0`), or the history would only be reachable while output happens to be on screen — the case where nobody needs it.
  - ⚠️ **Tests must never let the real agent spawn.** `codex` is genuinely installed on a dev machine, and the handler runs whatever it finds on PATH: a test that *prepends* a fake dir still fired the real `codex`, which waits on stdin, never exits, and poisons every test after it. `handlers.test.ts` **replaces** `process.env.PATH` with a dir holding only a stub, and stops the child in `afterEach`. ⚠️ **Replacing PATH is no longer sufficient on its own** — see `SAGYOU_DISABLE_BIN_FALLBACK` above, which the not-installed test must also set.
    - ⚠️ **A stub script therefore cannot call anything by bare name either** — the replaced PATH holds only the stub. The codex stubs echo stdin with `cat`, which resolved to nothing and killed the script with exit 127 before it printed, failing two guide tests for a harness reason while the handler was fine. Resolve such helpers to an **absolute path before** narrowing PATH.

## Data / Schema safety

The app persists state to a **SQLite database** (`kanban.db`) in `app.getPath('userData')`. There is **production data in the wild** — users have real tasks, habits, goals, and financial records stored on their machines.

Not everything lives in the DB. Also in `userData`:

| Path | Contents |
|---|---|
| `kanban.db` | the main store (projects, tasks, sprints, notes, goals, habits, financial tables, file metadata, `settings`) |
| `files/` | the actual uploaded file blobs — the `files` table only holds metadata, so deleting a row without the blob (or vice versa) orphans the other |
| `ai-config.json` | AI provider base URL, API key, model; optional `modelComplex` (chat routing), `codeAgent: {baseUrl,apiKey,model}` (native code agent, empty fields fall back via `resolveCodeAgentConfig`), and the ai-jail sandbox flags `sandboxEnabled` (absent = required) / `sandboxOnboardingDismissed` |
| `ai-conversations.json` | AI chat history (per chat: `messages`, `usage`, and `titleCustom` — all optional, absent on older files) |
| `agent-runs/` | archived code-agent runs: `index.json` (metadata the picker lists) + one `<id>.json` per run holding its frozen log and diff |
| `ai-run-metrics.json` | one record per agent run (model, steps, tokens, redundant searches, repeated reads, whether it hit the step cap), for comparing model efficiency over time — capped at `MAX_RUN_METRICS` |

Treat these with the same care as the DB — the same "production data in the wild" caveat applies.

- **Never remove or rename fields** on existing types without a migration or backward-compatible fallback (e.g. optional field with a default on load).
- **Never change the shape of persisted arrays or objects** in a breaking way (reordering, nesting, type changes).
- Adding new optional fields is safe — the store hydrates with `??` defaults and missing keys are silently ignored.

### Code path selection is a two-field pair

`Project.activeCodePathIds: string[]` is the source of truth for which code paths the AI reads. An **empty selection is a legitimate state** (the AI reads no code) — never backfill it from the remaining paths, e.g. on remove. Auto-selecting a folder the user didn't pick silently hands the assistant a directory to read. The legacy singular `Project.activeCodePathId` is **still written**, mirroring `activeCodePathIds[0]`, so older app versions and old backups keep resolving a selection. Go through `activeIds()` / `withActive()` in `store/kanban.ts` — never set either field by hand, or the two drift apart. `normalizeProject` on load migrates legacy singular data and drops ids whose code path no longer exists.

The `project_code_paths` SQLite table needed no migration: `active` was already a per-row flag, so multiple selected rows just means multiple `1`s. `persistAll` writes every selected id; the loader collects all `active` rows.
- **Always warn explicitly** before making any change that could corrupt or lose existing data on load (e.g. changing a field from `string` to `string[]`, removing a required field, changing an ID scheme). Flag it with: _"⚠️ Breaking schema change — existing data may be affected."_

### Monetary fields are decimal strings

`FinancialTransaction.amount`, `FinancialGoal.targetAmount`, and `ShoppingItem.price` are stored **in memory and in backups/JSON as canonical decimal strings** (e.g. `"1500.5"`), not numbers. All money arithmetic goes through `decimal.js` — use the `D()` helper and `Decimal` methods (`.plus/.minus/.times/.div`) in `components/financial/shared.ts`; only convert to `number` for display geometry (bar widths, percentages). `qty` stays a `number` (it's a quantity, not currency).

- On load, `normalizeList` migrates any legacy `number` values to canonical string via `moneyStr` — old data and old backups keep working.
- The SQLite columns for these fields are `TEXT` (`price`, `amount`, `target_amount`), storing decimal strings on disk. `qty` stays `REAL`. On insert, `moneyText()` in `main/store.ts` coerces number-or-string to a string.
- `migrateMoneyColumnsToText()` in `main/store.ts` upgrades existing databases: it detects the legacy `REAL` columns via `PRAGMA table_info` and rebuilds those three tables as `TEXT` (create `_new`, `CAST` copy, drop, rename — inside a transaction with foreign keys toggled off). Idempotent: skips tables already `TEXT`.

## Testing

Tests run in jsdom via Vitest. `ElectronStorage` is vi-mocked per test file (a `vi.mock('../../services/ElectronStorage', …)` factory at the top, before the store import — `setup.ts` only loads jest-dom) — tests call `useKanbanStore.getState()` directly to exercise store actions. Test files live in `src/renderer/src/__tests__/` under `store/`, `integration/`, `services/`, `utils/`, and `ai/` (the agent loop and the tool registry, with the provider stubbed).

Main-process code is tested too, under `src/main/__tests__/` — those files need `@vitest-environment node` (the suite defaults to jsdom, which the OpenAI SDK refuses to construct under). `handlers.test.ts` covers the real IPC handlers: it mocks `electron` just enough for `app.whenReady()` to run (that's what registers them), captures `ipcMain.handle`, and drives each channel against a **real local HTTP server** rather than a stubbed SDK — so SSE parsing, `tool_call` assembly, the `stream_options` 400 fallback, usage and error statuses are all exercised for real. `usage.ts`, `openai-client.ts` and `code-files.ts` are tested directly as plain modules.

⚠️ When testing path confinement, the file outside the root **must actually exist**. A test using `../nope.txt` passes whether or not the confinement works, because the handler rejects the missing file anyway — it proves nothing. `handlers.test.ts` puts the root inside a container with a real `secret.txt` sibling for this reason.

The `coverage/` directory is generated output — do not commit it.
